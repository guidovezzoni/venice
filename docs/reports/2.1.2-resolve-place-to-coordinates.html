Story

2.1.2 — Resolve Place Names to Coordinates

As a user, I want the app to resolve place names to coordinates so that routes can be calculated between my stops.

Branch

feature/2.1.2-resolve-place-to-coordinates (created from main at 47e750f)

Refinement Summary

Analysis revealed that the core coordinate resolution flow was already implemented in story 2.1.1 (Search Place by Name). The Place Details API call, domain model, ViewModel wiring, dialog auto-fill, and database storage are all in place.

The refinement re-scoped story 2.1.2 to focus on three remaining UX gaps:

  • Gap 1 — No loading indicator: When the user taps an autocomplete suggestion, the Place Details API call fires with no visual feedback. Fix: add isResolvingPlace state, show a progress indicator in the dialog, disable confirm while resolving.
  • Gap 2 — Error shown behind dialog: Place Details errors emit a Snackbar at screen level, which is hidden behind the open dialog. Fix: add placeDetailError state, show inline error in the dialog (matching the existing searchError pattern).
  • Gap 3 — Retry after failure: Already adequate — suggestions remain visible after failure so the user can tap again. The inline error message (Gap 2) will inform the user that they can retry.

Five acceptance criteria defined, covering the already-satisfied original criteria plus the new UX requirements. Unit and Compose UI test plans included.

Change Proposed

12 Jun 2026

Source: opsx:propose

Exploration Findings

Explored the existing codebase to understand integration points for the two UX gaps identified in the story refinement:

  • OnSuggestionSelected handler (TripDetailViewModel:191-200): launches a bare coroutine with no loading flag — no feedback until success/failure.
  • Error routing: On failure, emits TripDetailUiEffect.ShowError which renders as a Snackbar at screen level, hidden behind the open dialog.
  • Existing patterns identified: isSearchingPlaces + searchError inline display in StopForm; isLoading + confirm button disable in SetStopDialog; clearSearchState() for state cleanup.
  • Distinct concerns: isResolvingPlace is separate from isLoading — different semantics (no minimum duration, dialog-scoped fetch vs screen-level save).

Key Design Decisions

  • Separate isResolvingPlace flag (not reusing isLoading) — different semantics, no minimum duration
  • Inline error via placeDetailError state field — dialog is modal, Snackbar would be hidden
  • Resolving spinner inside StopForm body — consistent with isSearchingPlaces spinner placement
  • Error cleared on new search query, new suggestion selection, and dialog dismiss
