Overview

User story 9.2.1 (Send Events to Firebase Analytics) was opened for development on the branch feature/9.2.1-firebase-analytics-provider, created from main.

Story Refinement

The story was enriched during opening with comprehensive analysis and implementation guidance:

  • Acceptance criteria expanded from 17 to 24 criteria with detailed Firebase provider specifications
  • Boolean-to-String handling for is_first_trip parameter aligned with tracking plan requirements
  • AD_ID permission removed from manifest — analytics provider does not require advertising identifier
  • Comprehensive GDPR analysis documented: consent is assumed granted pending story 9.3.1 (Settings + Consent Gate); this is a deliberate, recorded temporary position as noted in the tracking plan
  • Firebase console setup requirements identified:
    • Both development and production app IDs must be registered
    • All 14 custom event definitions must be registered as String dimensions (event-parameter names)
    • All integer parameters (stop_count, leg_count, suggestion_count, suggestion_position) must be registered as custom metrics
    • Both user properties (trip_count_band, distance_unit) must be registered as custom user properties
  • Unit testing strategy established: FirebaseAnalyticsProvider tested by mocking Firebase SDK; success and failure paths verified; thread-safety validated via concurrent dispatch from multiple coroutine contexts
  • Documentation update plan: tracking plan already lists Firebase as the target backend; no plan updates needed

Key Concerns and Decisions

  • Warning Consent gate is deferred: Story 9.3.1 must deliver the consent gate before any release ships to EU users. The consent assumption is recorded in the tracking plan and is monitored as a blocker.
  • Info US data processing: Firebase's US-based processing is acceptable for current scope; GDPR concerns are handled by the consent gate deferral.
  • Info AD_ID manifest merge: Confirmed that the provider does not add the AD_ID permission to the manifest.

Change Proposed

August 21, 2026

Source: propose_change

Exploration Findings

Codebase exploration confirmed the analytics abstraction from stories 9.1.1 and 9.1.2 is fully in place: AnalyticsProvider interface, CompositeAnalyticsClient with Hilt multibinding, DebugAnalyticsProvider as the structural template, all 14 events in AnalyticsEvent.kt, and both user properties in AnalyticsUserProperty.kt. No Firebase dependencies exist in the project yet.

Notable finding: AnalyticsProvider in code has no shouldLog method, contrary to the analytics guidelines document. This is pre-existing drift, not blocking for 9.2.1 since Firebase receives all events.

CI already exists (.github/workflows/ci.yml) — contradicting docs/improvements/github-ci-setup.md which claims "no CI/CD".

Key Design Decisions

  • Provider mirrors DebugAnalyticsProvider pattern with constructor-injected FirebaseAnalytics
  • Generic Bundle mapping from event.properties map, with ScreenViewed as the sole special case
  • Boolean values generically converted to "true"/"false" Strings (not TripCreated-specific)
  • Platform-limit validation gated by injectable isDebugBuild flag — throws in debug, logs in release
  • AD_ID kept (explicit deviation from source story AC 19, recorded in proposal, design, and tasks)
