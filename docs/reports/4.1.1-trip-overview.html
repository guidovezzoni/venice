4.1.1 — Trip Overview with Per-Leg Breakdowns

Story: 4.1.1 Branch: feature/4.1.1-trip-overview Created: 2026-07-10

Story Refined & Opened

10 July 2026

Source: open_user_story

Acceptance Criteria Analysis

Most acceptance criteria are already satisfied by the existing TripDetailScreen composable:

  • Stop list with progress status
  • Per-leg distance and duration display
  • Trip totals (distance and duration)
  • Entry points for stop management features
  • Calculate route button

Genuine New Work

Two concrete work items identified:

  1. Display real trip name in header: Currently the header displays a hardcoded "Trip Detail" string. Must be replaced with the actual trip name from the Trip domain model.
  2. Explicit route-not-calculated / stale prompt: Add user-facing guidance when the route has not been calculated or is stale relative to stop changes.

Out of Scope

  • Navigation to stop details: Deferred to Epic 5 (stories 5.1.1 and 5.1.2)
  • Editing trip name: Not part of this story; would require a separate feature

Data and API

No new API endpoints required. Work uses existing local data sources (Trip domain model, existing Directions API integration) and existing composable infrastructure.

Security & Privacy Considerations

  • GDPR: Trip names and coordinates are personal data. Must never be logged or transmitted to analytics services.
  • Security: Trip name rendered as plain text only; no user input or rich formatting.

Performance Considerations

Adding a third observed data stream (Trip) to the screen's ViewModel must not cause redundant recomposition. Verify that the Trip state is only emitted when relevant data actually changes, not on every domain operation.

Change Proposed

Exploration Findings

  • TripDetailScreen top bar hardcoded to "Trip Detail" — no trip name observation exists in the ViewModel
  • TripDetailViewModel already computes route completeness (legs.size == stops.size - 1 && stops.size >= 2) for totals — the same signal drives the new prompt
  • TripDao.getById exists as a one-shot suspend query — a new Flow-returning observeById is needed
  • TripRepository has no single-trip read method — needs observeTripById + a new ObserveTripUseCase
  • Route invalidation hard-deletes all legs — no "stale" flag exists; missing and stale are identical in the data model

Questions & Clarifications

QuestionAnswer
Should "never calculated" and "stale after edit" show different messages? No — single generic prompt, no schema change
Should the prompt appear with fewer than 2 stops? No — only when 2+ stops (same guard as Calculate route button)
Should the prompt be tappable or purely informational? Tappable — dispatches existing OnCalculateRouteClicked intent
What should the top bar show while trip name is loading? Static fallback "Trip Detail" until the real name arrives

Key Design Decisions

  1. TripDao.observeById is a new Flow-returning query (existing getById left untouched)
  2. tripName: String? (null = not yet loaded) with null-coalescing fallback in the composable
  3. isRouteRecalculationPromptVisible: Boolean derived in the existing combine collector alongside totals
  4. Extended combine result uses a private data class (TripTotalsAndPromptState) instead of positionally ambiguous Triple
  5. RouteRecalculationPrompt in its own file, mirroring TripTotalSummary / TripProgressSummary
  6. No new intents — prompt reuses OnCalculateRouteClicked
  7. No schema/migration change — purely additive DAO query
