User Story

2.1.1 — Search for a Place by Name

As a user, I want to search for a place by name when adding or editing a stop so that I don't have to know exact coordinates.

Branch

Refinement Summary

The original user story was high-level. The refined version adds:

  • 10 detailed acceptance criteria covering search integration, debouncing, suggestion display, selection, read-only coordinates, manual fallback, edit mode, error handling, loading indicator, and session token lifecycle.
  • Full technical specification across 9 new files (domain models, repository interface/implementation, mappers, use cases, DI module) and 8 files to modify (gradle, build config, UI composables, state, intents, ViewModel, strings, app initialisation).
  • Google Places SDK (New) integration via com.google.android.libraries.places:places:4.2.0 with session-token-based billing.
  • API key security: stored in local.properties (gitignored), surfaced via BuildConfig, restricted to app package and signing certificate.
  • Clean Architecture compliance: domain layer uses Any for session token to avoid SDK type leakage; mappers reside in the data layer.
  • Non-functional analysis: GDPR (no PII sent beyond search query), performance (debounce + coroutine cancellation), accessibility (focusable suggestions, screen reader announcements), offline graceful degradation.
  • 19-item completion checklist including on-device manual verification.

Exploration Findings

Investigated 8 key design questions before proposing. Findings grounded in Google Places SDK (New) documentation via Context7:

  • Places SDK API surface: FindAutocompletePredictionsRequest + FetchPlaceRequest with AutocompleteSessionToken for billing (~$0.017/session). Task-based API requires kotlinx-coroutines-play-services for .await().
  • Session token: Managed entirely inside PlaceSearchRepositoryImpl — domain layer never sees it. Auto-created on first search, consumed on place detail fetch, cleared on dialog dismiss.
  • Debouncing: Job cancellation pattern (300ms) — matches existing ViewModel style.
  • State split: Search state (suggestions, loading, error) in ViewModel; form fields (placeName, lat, lng) remain as local composable state. Coordinate writeback via selectedPlaceDetail field consumed by LaunchedEffect.
  • Read-only coordinates: Local composable boolean, set on selection, cleared on manual edit.
  • SDK initialisation: Places.initializeWithNewPlacesApiEnabled() in VeniceApplication.onCreate(); PlacesClient provided via Hilt.

Questions Asked and Answers

All 8 design questions were explored and resolved during the exploration phase. No blocking ambiguities remained — the user confirmed the approach was solid and approved moving to proposal.
