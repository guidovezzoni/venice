Key Refinement Insights

  • Exception vs. Event Separation: The two-channel model is maintained — exceptions route to Crashlytics crash reporting with full stack traces, while bounded failure events go to product analytics. No freeing of exceptions into event parameters.
  • User Properties Forward Correctly: Both trip_count_band and distance_unit are forwarded as Crashlytics custom keys, enabling segmentation of crash reports by user state
  • Boolean-to-String Conversion: The tracking plan specifies is_first_trip as Boolean at the domain level but Firebase requires String — Crashlytics does not have this constraint, so the conversion is provider-specific
  • Provider Registration: DI wiring via @Binds @IntoSet, consistent with the existing FirebaseAnalyticsProvider pattern

Change Proposal

Source: propose_change

Exploration Findings

Sub-agent explored the analytics architecture, DI setup, build configuration, and test patterns:

  • Analytics architecture: AnalyticsTracking interface with logEvent, setUserProperty, trackException, and default trackFailure. CompositeAnalyticsClient fans out to all providers via multibound set.
  • Pattern to follow: FirebaseAnalyticsProvider — constructor-injected SDK, private companion object for constants, thread-safe by delegation, no mutable state.
  • No shouldLog method: Per-event filtering is done inside each provider's logEvent as an early-return guard clause, not via an interface gate.
  • trackException no-op: FirebaseAnalyticsProvider.trackException is an explicit no-op with a comment pointing at "story 9.2.2" — this story gives that channel its first real implementation.
  • DI ready: @Multibinds already exists in AnalyticsModule.kt; adding a second @IntoSet binding is mechanical.
  • Build infrastructure: google-services.json already handled, CI decodes from secret, no new secrets needed. settings.gradle.kts repo filter already covers com.google.firebase.

Key Design Decisions

  • Independent provider: Separate class from FirebaseAnalyticsProvider, not an extension — different SDKs, different failure semantics, independent consent lifecycle.
  • logEvent never calls recordException: Non-fatals only from trackException; OperationFailed only sets error_type custom key. Specced scenario guards this invariant.
  • operation key before recordException: Ensures the operation context is attached to the correct non-fatal report. Verified by ordered mock assertion.
  • All custom keys are String: Uniform setCustomKey(String, String) — no type branching needed.
