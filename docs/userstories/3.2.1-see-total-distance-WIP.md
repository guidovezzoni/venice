# 3.2.1 — See Total Distance of the Roadtrip

**Epic:** 3 — Route Calculation
**Feature:** 3.2 — Trip Totals
**Status:** Refined (WIP)

---

## 1. Functionality Overview

On the **Trip Detail** screen the user can already calculate a route and see the
distance and duration of each individual leg (stories 3.1.1–3.1.3). This story adds a
single **total distance** figure for the whole trip: the sum of every calculated leg
distance, presented once, in a clear and locale-aware format.

The total gives the user a sense of the overall scale of the journey ("this trip is
1,240 km") without adding up the legs themselves.

### Behaviour at the "what" level

- The trip overview shows a **total distance** for the trip.
- The total equals the **sum of all individual calculated leg distances**.
- The total uses the **same locale-aware unit and formatting rules** already applied to
  individual legs (metres / kilometres for metric locales, miles for imperial locales —
  see `DistanceFormatter`), so the units are consistent across the screen.
- The total **updates automatically** whenever the route is (re)calculated, without any
  extra user action.
- When the trip's route is **not currently available** (no route has been calculated yet,
  or a stop change has invalidated the previously calculated route), the total is shown as
  **unavailable** rather than showing a misleading or zero value.

### Route-availability model (grounded in current code)

The existing invalidation is **all-or-nothing**: any stop mutation (set, edit, move,
remove) deletes **all** legs for the trip (`InvalidateRouteUseCase` →
`deleteLegsForTrip`). Consequently, in the current implementation the stored legs are
either:

- **Complete** — one leg exists for every consecutive pair of placed stops
  (`legs.size == placedStopCount − 1`, with `placedStopCount ≥ 2`), or
- **Absent** — no legs exist (route never calculated, or invalidated by a stop change).

A genuinely *partial* set of legs does not occur today. The refined acceptance criteria
therefore treat "route not complete" as a single **unavailable** state. The original
story's "partial with a warning" wording is preserved below but is **not required** given
the current all-or-nothing model; if per-leg invalidation is introduced in a future story,
a partial/stale total can be revisited then.

> **Scope note — trip list summary.** The original story also mentions showing the total
> in the trip list (1.1.2). The trip list currently loads only a stop *count*
> (`TripWithStopCount`) and has no access to leg data, so surfacing a total there is
> **materially larger scope** (loading/aggregating legs per trip in the list query). This
> is **recommended to be deferred to its own story** and is treated as **out of scope**
> here. The orchestrator can confirm.

## 2. Fields to be Updated

No new domain model or persisted field is required — the total is **derived**, not stored.

| Field | Location | Type | Purpose |
|-------|----------|------|---------|
| `formattedTotalDistance` (new) | `TripDetailUiState` | `String?` | Pre-computed, display-ready total distance string. `null` (or an explicit "unavailable" sentinel) when the route is not complete. Follows the existing pattern of `formattedLegDistances` / `formattedLegDurations` — **formatting happens in the ViewModel, never in the composable.** |
| `isRouteComplete` *(optional, if the UI needs to distinguish "unavailable" styling)* | `TripDetailUiState` | `Boolean` | Whether a complete route is available. Only add if the screen genuinely needs it beyond a nullable string; keep the state minimal otherwise. |

- The total is computed from the **existing** `Leg.distanceMetres` values already present
  in `TripDetailUiState.legs`; **no new domain field on `Leg` or `Trip`**.
- Summation must use a width that cannot overflow for realistic trips (sum of `Int`
  metres across up to 24 legs — accumulate as a `Long`/`Int` sum safely; see Performance).

---

## 3. Endpoints

**None.** This is a purely local, derived value. No network call, no new Google Routes /
Places request. The data already lives in the local `legs` table populated by story 3.1.1.

## 4. Files to Modify (intent, not solution)

Described by intent; the exact structure is for the propose/design phase.

**UI state**
- `ui/state/TripDetailUiState.kt` — add the pre-computed total distance field (and, if
  justified, a completeness flag).

**ViewModel**
- `ui/viewmodel/TripDetailViewModel.kt` — in the existing `observeLegsUseCase(tripId)`
  collector (where `formattedLegDistances` is already computed), also compute the
  total: sum the leg distances **only when the route is complete**, format via the
  existing distance formatter, and emit it in state; otherwise emit the unavailable value.
  The completeness check needs the placed-stop count, which the ViewModel already derives
  from the stops flow — combine the two sources so the total reflects both legs and stops.

**Formatting util**
- `ui/util/DistanceFormatter.kt` — reuse `formatDistance(...)` as-is for the total. No
  new formatter is expected; a total is just a distance. Only touch this file if a
  genuinely new formatting need surfaces during design (not anticipated).

**Composable(s)**
- `ui/screens/tripdetail/` — add a small **stateless, presentational** composable
  (e.g. `TripTotalSummary`) that renders the pre-formatted total (and an "unavailable"
  label when applicable). It must receive display-ready strings as parameters and contain
  **no logic** (consistent with `LegSummary` / `TripProgressSummary`).
- `ui/screens/tripdetail/TripDetailScreen.kt` — place the total summary in the overview
  (a sensible location is near the route-calculation button / trip footer). Add it as a
  `LazyColumn` item.

**Strings**
- `res/values/strings.xml` (UK English base) — add user-facing strings, e.g.
  `trip_detail_total_distance_label` (label + value) and
  `trip_detail_total_distance_unavailable`. Update any other present locale files
  accordingly (per i18n guideline). Use an ellipsis character where relevant, no "...".

**Previews**
- Update/extend previews in the new composable and in `TripDetailScreen.kt` to cover the
  total in: available/complete state and unavailable state (so every new `UiState` field
  has non-default preview coverage).

## 5. Unit Testing

Follow the project testing guidelines (JUnit 4, MockK, GIVEN/WHEN/THEN names, extract
expected value before asserting, ≥95% coverage, `createViewModel(...)` factory helper).

**ViewModel tests (`TripDetailViewModelTest`)** — behaviour via observed `uiState`:
- GIVEN a complete set of legs WHEN legs are observed THEN `formattedTotalDistance` equals
  the formatted sum of all leg distances.
- GIVEN two legs of 10 000 m and 2 500 m WHEN observed THEN the total reflects 12 500 m
  formatted in the active locale (assert the exact expected formatted string, computed
  independently of the production summation call site where practical).
- GIVEN no legs but ≥2 placed stops (route not yet calculated / invalidated) WHEN observed
  THEN the total is the **unavailable** value.
- GIVEN fewer legs than expected for the placed stops (incomplete) WHEN observed THEN the
  total is **unavailable** (guards the completeness rule).
- GIVEN fewer than two placed stops WHEN observed THEN the total is **unavailable** (no
  route possible).
- GIVEN legs then a stop mutation that invalidates the route WHEN observed THEN the total
  transitions to **unavailable**.
- Metric vs imperial: verify the total uses the same unit selection as individual legs
  (locale-driven), consistent with existing `DistanceFormatter` tests.

**Formatter** — `DistanceFormatterTest` already covers `formatDistance`. Add a case only
if a new summation/rounding edge (e.g. very large totals) is not already covered.

**Compose UI tests (`TripDetailScreenTest`, `androidTest`)** — composable in isolation via
`uiState`:
- Total is displayed with the expected value when `formattedTotalDistance` is present.
- The "unavailable" label is displayed when the total is absent.
- Use `onNodeWithText` / `onAllNodesWithText[index]` where the value collides with a leg
  distance string.

**Test files required:** update existing `TripDetailViewModelTest` and
`TripDetailScreenTest`; add a preview + (optional) isolated test for the new

## 7. Security — Issues & Mitigations

- **No new attack surface.** No new endpoint, no new input, no new permission. The total
  is derived from data already stored locally.
- **No secrets involved.** No API keys touched (no new network call).
- **Integer summation integrity.** Ensure summation cannot overflow or produce a negative
  value from corrupted data; clamp/validate defensively and treat implausible values as
  unavailable rather than rendering garbage. Low severity.

---

## 8. Performance — Issues & Mitigations

- **Cheap computation.** Summation over ≤24 legs is trivial; runs inside the existing legs
  collector — no extra flow, DB query, or network round-trip.
- **Compute off the UI thread / in the ViewModel.** Formatting and summation must happen
  in the ViewModel (already the case for leg formatting), keeping the composable purely
  presentational and avoiding recomposition-time work.
- **Avoid redundant recomputation.** Recompute only when `legs` (or the stop set feeding
  the completeness check) actually changes; reuse the existing collector rather than adding
  a new subscription.
- **Overflow safety.** Accumulate the sum in a type that cannot overflow for the maximum
  supported stops/distances (a `Long` accumulator is safe even at planetary distances).

---

## 9. GDPR & Sensitive Information — Issues & Mitigations

- **No personal data processed or created.** The total is an aggregate number derived from
  route geometry already stored on-device; it is not personal data on its own.
- **No new data collection, storage, or transmission.** Nothing leaves the device; nothing
  new is persisted.
- **Analytics.** If any analytics event is added, log only non-identifying facts (e.g. that
  a total was displayed) and **never** raw coordinates, place names, or precise distances
  that could reveal a user's location or itinerary. Prefer adding **no** new analytics for
  this passive display unless there is a clear product need.

---

## 10. Other Non-Functional Requirements

- **Accessibility.** The total must have a meaningful, screen-reader-friendly label
  (content description) and adequate contrast/typography via Material 3 theme tokens; do
  not rely on colour alone to signal "unavailable".
- **Localisation.** All user-facing text extracted to `strings.xml` (UK English base) and
  propagated to other present locales. Number/unit formatting stays locale-aware and
  consistent with individual legs.
- **Consistency.** Visual style should match existing summary rows (`LegSummary`,
  `TripProgressSummary`) — same padding constants pattern, `onSurfaceVariant` treatment,
  Material 3 typography.
- **State minimalism (MVI).** Add only the fields the UI truly needs; keep `UiState`
  immutable and the composable stateless. Extract any literals to private constants in
  their own file/class.
- **Configuration changes.** Because the value is derived in the ViewModel from observed
  flows, it survives rotation without extra handling.

## 11. Definition of Done (Acceptance Criteria)

Observable outcomes:

1. The trip overview displays a **total distance** for the trip.
2. When a complete route is available, the total **equals the sum of all individual leg
   distances** and uses the **same locale-aware unit/format** as the individual legs.
3. The total **updates automatically** when the route is recalculated (no extra user
   action).
4. When no complete route is available (never calculated, or invalidated by a stop
   change), the total is shown as **unavailable** — not as zero or a misleading value.
5. The total is **derived** — no new network call and no new persisted field.

Process/quality gates:

6. New/updated unit tests (ViewModel) and Compose UI tests pass; coverage ≥95% on new code.
7. Every new `UiState` field has non-default preview coverage; all new composables have
   previews wrapped in `HeadingToVeniceTheme` with `showBackground = true`.
8. New user-facing strings extracted to `strings.xml` (and mirrored to other locales);
   ellipsis character used where relevant.
9. `./gradlew check` and `./gradlew build` pass; on-device verification confirms the total
   appears, matches the leg sum, updates on recalculation, and reads "unavailable" after a
   stop change until recalculated.

## Original user story

### 3.2.1 — See Total Distance of the Roadtrip

**Epic:** Route Calculation
**Feature:** Trip Totals

#### User Story

As a user, I want to see the total distance of the entire roadtrip so that I can gauge the overall scale of my journey.

#### Description

The trip overview displays the sum of all leg distances as the total trip distance.

#### Acceptance Criteria

- Total distance is displayed on the trip overview screen.
- It equals the sum of all individual leg distances.
- It updates when the route is recalculated.
- If any leg is uncalculated (route is stale), the total is shown as unavailable or partial with a warning.

#### Technical Notes

- Computed from stored `Leg.distanceMeters` values — no additional API call needed.
- Can be calculated in the ViewModel or as a derived property on the Trip domain model.
- Also shown in the trip list (1.1.2) as a summary.
