# 3.1.1 — Calculate Route Between Consecutive Stops

**Epic:** Route Calculation
**Feature:** Leg Calculation

## User Story

As a user, I want the app to calculate the route between consecutive stops when I explicitly request it, so that I know the distance and time for each leg.

## Description

When the user has set at least a starting point and destination (minimum 2 stops), the app provides a "Calculate route" button on the trip detail screen. Pressing it calls the Google Directions API to compute the route. The API returns distance, duration, and an encoded polyline for each leg (pair of consecutive stops). Results are persisted locally so the user can view them without re-fetching.

When stops are subsequently added, removed, reordered, or edited, stored legs are invalidated (deleted) and the user can recalculate by pressing the button again.

## Acceptance Criteria

1. A "Calculate route" button is visible on the trip detail screen when at least 2 stops exist.
2. Pressing the button triggers a single Google Directions API request with all stops (origin + destination + intermediate waypoints).
3. While the request is in-flight, a loading indicator is shown and the button is disabled.
4. On success, distance (metres) and duration (seconds) are stored locally for each leg.
5. The encoded polyline is stored for each leg (not rendered in this story, but persisted for future use).
6. On failure (network error, invalid stops, API quota), the user sees an inline error message.
7. Previously stored legs are deleted and replaced when the route is recalculated.
8. When stops are added, removed, reordered, or edited after a calculation, all legs for that trip are invalidated (deleted) and the "Calculate route" button is shown again.

## Fields and Data Model

### Domain Model: `Leg`

| Field | Type | Description |
|-------|------|-------------|
| `id` | `String` | UUID primary key |
| `tripId` | `String` | FK to Trip |
| `fromStopId` | `String` | FK to the origin Stop of this leg |
| `toStopId` | `String` | FK to the destination Stop of this leg |
| `distanceMetres` | `Int` | Distance in metres |
| `durationSeconds` | `Int` | Duration in seconds |
| `encodedPolyline` | `String` | Google-encoded polyline string |

### Database Entity: `LegEntity`

Same fields as the domain model, stored in a `legs` table with:
- Primary key on `id`
- Foreign key on `tripId` → `trips.id` (ON DELETE CASCADE)
- Index on `tripId`

## API Endpoint

**Google Directions API** (HTTP REST)

```
GET https://maps.googleapis.com/maps/api/directions/json
    ?origin={lat},{lng}
    &destination={lat},{lng}
    &waypoints={lat1},{lng1}|{lat2},{lng2}|...
    &key={MAPS_API_KEY}
```

- Origin: first stop (order 0) coordinates
- Destination: last stop (highest order) coordinates
- Waypoints: intermediate stops in order, pipe-separated
- Response: `routes[0].legs[]` contains `distance.value`, `duration.value`, `overview_polyline.points` per leg

## Security Considerations

- **API key exposure**: The `MAPS_API_KEY` is stored in `local.properties` (already gitignored) and injected via `BuildConfig`. The key should be restricted in the Google Cloud Console to the app's package name and signing certificate.
- **No user data sent to API**: Only latitude/longitude coordinates are sent. No PII.
- **Input validation**: Coordinates are validated as non-zero before making the API call.

## Performance Considerations

- **Single API call**: All waypoints are sent in one request rather than N-1 separate calls.
- **Local caching**: Results are persisted in Room so the route is not re-fetched on every screen visit.
- **Lazy invalidation**: Legs are deleted (not recalculated) when stops change, avoiding unnecessary network calls.
- **Minimum loading duration**: Per project convention, the loading state should display for at least 500ms to avoid UI flicker.

## GDPR and Sensitive Information

- No personal data is stored in the `legs` table — only route geometry and distances.
- Coordinates sent to Google are trip waypoints, not the user's live location (that is a Level 2 concern).
- No additional consent is required beyond what's already in place for Google Places.

## Non-Functional Requirements

- **Offline resilience**: The app must not crash if the API is unreachable. A clear error message is shown and the user can retry.
- **Waypoint limit**: Google Directions API allows a maximum of 25 waypoints (origin + destination + 23 intermediate). The app already caps intermediate stops at 23 (from story 1.2.3). No additional validation needed.
- **Future extensibility**: The `RouteRepository` interface accepts an origin parameter so that in Level 2 the live GPS position can be injected as the origin instead of the first stop.

## Definition of Done

1. "Calculate route" button appears when ≥ 2 stops exist
2. Pressing it calls the Google Directions API and persists legs locally
3. Loading indicator shown during API call (minimum 500ms)
4. Error message shown on API failure
5. Legs are replaced on recalculation
6. Legs are invalidated (deleted) when stops are mutated
7. All unit tests pass (≥ 80% coverage on new code)
8. Compose UI tests cover button states and error display
9. App builds cleanly (`./gradlew check` passes)

## Original User Story

### User Story

As a user, I want the app to calculate the route between consecutive stops when I finalise my plan so that I know the distance and time for each leg.

### Description

When the user has set at least a starting point and destination, the app calls the Google Directions API to calculate the route. The API returns distance, duration, and route geometry for each leg (pair of consecutive stops). Results are stored locally so the user can view them without re-fetching.

### Acceptance Criteria

- Route calculation is triggered when the user explicitly requests it (e.g., a "Calculate route" button) after setting at least two stops.
- The app sends a single Directions API request with all stops (origin, destination, and intermediate stops as waypoints).
- Distance and duration are stored for each leg.
- If the API call fails (network error, invalid stops), the user is informed with a clear error message.
- Previously stored legs are replaced when the route is recalculated.

### Technical Notes

- **API:** Google Directions API. Send origin, destination, and up to 23 intermediate waypoints in a single request. The response contains a `legs[]` array with one entry per consecutive stop pair.
- **Trigger:** Calculation happens on plan creation/edit (not on-demand every time the user views the trip). Store results in the local database.
- **Data model:** `Leg(id, tripId, fromStopId, toStopId, distanceMeters, durationSeconds, polyline)` — store the encoded polyline too, even if not rendered in Level 1, to avoid re-fetching later if a map view is added.
- **Invalidation:** Legs are invalidated when stops are added (1.2.3), removed (1.2.6), reordered (1.2.4), or edited (1.2.5). Show a visual indicator that the route is stale and needs recalculation.
- **Level 2 consideration:** In Level 2, the same API is called with the user's live GPS coordinates as origin instead of the last departed stop's coordinates. Design the API client so the origin parameter is injectable.
