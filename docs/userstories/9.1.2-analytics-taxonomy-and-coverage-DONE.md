# 9.1.2 — Implement the Analytics Taxonomy and Close Coverage Gaps

**Epic:** Analytics
**Feature:** Analytics Foundation
**Status:** Refined
**Depends on:** 9.1.1 (analytics abstraction upgrade) — DONE

## User Story

As a product owner, I want the app to emit a consistent, analysable set of events covering every user
action, so that once a real analytics backend is connected I can answer concrete questions about how
people plan road trips — rather than discovering the data is unusable.

## Description

The current 10-event taxonomy will not survive contact with a real analytics backend. Almost every
event carries a raw UUID (`trip_id`, `stop_id`), and high-cardinality parameters collapse into GA4's
`(other)` bucket while consuming the limited custom-dimension budget. `operation_failed` forwards
`error.message` verbatim, which is both unbounded cardinality and a live PII path — a Places or
Directions error can contain a place name the user typed. `stop_set` emits `stopType.name`, producing
`STARTING_POINT` in an otherwise `snake_case` dataset.

Several shipped features also emit nothing at all.

This story replaces the taxonomy with the 14 events defined in `docs/analytics/tracking-plan.md`, built
to answer four stated product questions: funnel completion, feature adoption, reliability, and trip
shape. Raw identifiers are replaced throughout by low-cardinality aggregates — `stop_count`,
`leg_count`, `stop_type`, banded distances and durations.

**Doing this now is deliberate and time-critical.** Nothing consumes these events yet, so renaming the
whole set costs nothing: no historical data, no dashboards, no funnels. That window closes permanently
the moment story 9.2.1 ships Firebase.

### Failure paths: dual-channel emission

Every failure path that currently emits only an `OperationFailed` event must also call
`trackException(throwable, operation)` on the same analytics client. The event answers "how often"
(bounded enums only); the exception answers "where and why" (full throwable to crash reporting).

The following failure paths currently exist in the ViewModels:

- `TripListViewModel.createTrip()` — `OPERATION_CREATE_TRIP`
- `TripDetailViewModel.setStop()` — `OPERATION_SET_STOP`
- `TripDetailViewModel.editStop()` — `OPERATION_EDIT_STOP`
- `TripDetailViewModel.removeStop()` — `OPERATION_REMOVE_STOP`
- `TripDetailViewModel.moveStop()` — `OPERATION_MOVE_STOP`
- `TripDetailViewModel.markStopDeparted()` — `OPERATION_MARK_DEPARTED`
- `TripDetailViewModel.calculateRoute()` — `OPERATION_CALCULATE_ROUTE`

New failure paths to add:

- `TripDetailViewModel.undoMarkStopDeparted()` — `UNDO_MARK_DEPARTED`
- `TripDetailViewModel` place search failure — `SEARCH_PLACE`
- `TripDetailViewModel` place detail failure — `RESOLVE_PLACE`

### Enumerated values become enums

Loose `String` constants in the `AnalyticsEvent` companion are replaced by enums, each carrying an
explicit `value: String` in `snake_case`. Each enum gets its own file per the project's
one-class-per-file rule.

| Enum | Kind | Notes |
|------|------|-------|
| `DistanceBand` | maps | `from(metres)` — bands continuous distance into categories |
| `DurationBand` | maps | `from(seconds)` — bands continuous duration into categories |
| `CountBand` | maps | `from(count)` — bands trip count for the `trip_count_band` user property |
| `AnalyticsScreen` | labels | Screen name vocabulary (`trip_list`, `trip_detail`) |
| `StopTypeParam` | maps | Translates the domain `StopType` to analytics `snake_case` values |
| `AnalyticsErrorType` | labels | Error classification vocabulary (`network`, `timeout`, etc.) |
| `AnalyticsOperation` | labels | Already exists; needs `UNDO_MARK_DEPARTED`, `SEARCH_PLACE`, `RESOLVE_PLACE` added |

Events emit `.value`, never `.name`. This structurally prevents the `STARTING_POINT` casing bug.

`CountBand` must be a top-level type, not nested inside `AnalyticsEvent`. It is used only by
`AnalyticsUserProperty` (for `trip_count_band`) and by no event, so nesting it under `AnalyticsEvent`
would put a vocabulary inside a type that never references it.

### User properties

Two user properties must be set via `AnalyticsClient.setUserProperty(...)`:

| Property | Type | Values | Set when |
|----------|------|--------|----------|
| `trip_count_band` | String | `0`, `1`, `2_5`, `6_plus` | Trip list loads, or a trip is created/removed |
| `distance_unit` | String | `metric`, `imperial` | App start — before the first event |

These require concrete subclasses of `AnalyticsUserProperty` (replacing the current `ForTesting` placeholder). No event parameter shares a name with a user property.

### Error classification

An `AnalyticsErrorClassifier` must classify throwables into bounded `AnalyticsErrorType` values:
`network`, `timeout`, `not_found`, `permission_denied`, `quota_exceeded`, `persistence`, `unknown`.
This replaces passing raw `error.message` strings, which are unbounded cardinality and a PII vector.

### TODO resolution

The TODO at `TripDetailViewModel.kt` line 148 ("a dedicated analytics event for total-duration display
should be designed") is resolved by this story: `route_calculated` now carries `duration_band` and
`distance_band`, which answer the trip-shape question (Q4) that the TODO was deferring. No separate
total-duration event is needed.

## Security

### Potential issues and mitigations

1. **PII in error messages** — The current `OperationFailed` event passes `error.message` verbatim,
   which can contain user-typed place names from Places API or Directions API error responses.
   **Mitigation:** Replace with a bounded `AnalyticsErrorType` enum classified from the throwable's
   type, never its message content. The throwable message is passed only to `trackException`, which
   routes to crash reporting (not product analytics).

2. **Identifier leakage** — Current events carry raw UUIDs (`trip_id`, `stop_id`) that could
   theoretically be used to correlate user activity if the analytics backend were compromised.
   **Mitigation:** Replace all identifiers with aggregate parameters (`stop_count`, `is_first_trip`,
   `stop_position`). No event in the new taxonomy carries any identifier.

3. **Debug provider in release** — Already mitigated by story 9.1.1 (moved DI binding to `debug`
   source set). This story does not change that protection.

## Performance

### Potential issues and mitigations

1. **Banding calculations on every event** — `DistanceBand.from()` and `DurationBand.from()` perform
   simple numeric comparisons. The cost is negligible (a handful of integer comparisons) and does not
   warrant caching or optimisation.

2. **Error classification** — `AnalyticsErrorClassifier` inspects the throwable type via `is` checks.
   This is a constant-time operation on the failure path, which is already the slow path.

3. **User property updates** — `trip_count_band` is set on trip list load and trip creation/removal.
   These are infrequent operations. The analytics client fans out to providers (currently only the
   debug Logcat provider), so the cost is one `Log.d` call.

4. **No additional network calls** — All parameter data is derived from values already in memory
   (UI state, domain model fields). No new API calls, database queries, or I/O operations are
   introduced by this story.

## GDPR and Sensitive Information

### Potential issues and mitigations

1. **Privacy floor enforcement** — The new taxonomy carries no personal data: no identifiers, no free
   text, no coordinates, no place names, no trip names. This is enforced structurally by the sealed
   class constructor parameters — a non-enum, non-primitive value cannot reach a provider.

2. **Error message as PII vector** — `error.message` currently reaches the analytics event stream.
   A Places API error can contain the user's search query (a place name, which is personally
   meaningful data). **Mitigation:** `error_type` replaces `error_message`. The raw message is
   available only in the crash-reporting channel (`trackException`), which is a separate system
   with its own data retention and access controls.

3. **Coordinates in navigation events** — `navigateToStop()` currently passes `latitude` and
   `longitude` to the UI effect for the geo: URI. The analytics event (`navigation_launched`) must
   carry only `stop_type` and `stop_position`, never coordinates. This is enforced by the sealed
   class constructor accepting only `StopTypeParam` and `Int`.

4. **User properties and identification** — `trip_count_band` and `distance_unit` are low-cardinality
   and non-identifying. Neither reveals personal information. No user ID is set (no authentication
   until Epic 8).

5. **Consent posture** — Consent is currently assumed granted (documented in the tracking plan). This
   story does not change the consent posture. Story 9.3.1 will introduce a consent gate. The privacy
   floor in this taxonomy means the data collected without explicit consent is non-personal.

## Other Non-Functional Requirements

1. **Backward compatibility** — No backward compatibility concern. The only consumer is the debug
   Logcat provider; there are no dashboards, funnels, or stored data to break.

2. **Testability** — Every new enum, the error classifier, and the banding functions must be covered
   by unit tests. The `core/analytics/` package is not Kover-excluded, so all new code counts toward
   the 95% coverage threshold.

3. **Maintainability** — The sealed class taxonomy makes the full event set readable in one file and
   makes an untracked event a compile error. Enums with `.value` make casing bugs impossible.

4. **Thread safety** — All analytics calls go through `CompositeAnalyticsClient`, which delegates to
   an immutable provider set. Each provider is required to be thread-safe (documented in 9.1.1).
   No new threading concerns are introduced.

5. **Tracking plan consistency** — Every event in the code must have a tracking-plan entry and vice
   versa. This is verified by inspection during review and on-device verification.

## Technical Notes

- **Sequencing matters.** Do this before 9.2.1. After a real backend ships, every rename becomes a
  breaking change to accumulated data.
- **Aggregate parameters need data the ViewModel may not have to hand.** `stop_count` after a removal,
  `leg_count` and banded totals on route calculation, `stop_position` for departures — check what is
  already in `TripDetailUiState` (which holds `legs`, `formattedTotalDistance`, and the stop lists)
  before adding new plumbing.
- **`distance_band` and `duration_band` should band the raw values**, not parse the formatted display
  strings. `Leg` carries the raw distance and duration; the formatters are for the UI.
- `distance_unit` is already derived by `isImperialLocale()` in `DistanceFormatter.kt` — reuse that
  determination rather than re-deriving it.
- Band boundaries in the tracking plan are a first guess at a road-trip distribution. They are cheap to
  change now and expensive once data accumulates, so prefer more bands over fewer.
- Conventions: `docs/guidelines/guidelines-analytics.md`.
- `core/analytics/` is not Kover-excluded — every new enum, the classifier, and the banding functions
  need tests to clear the 95% bound.
- **`route_state` for `trip_opened`** needs to be derived from the trip's stop and leg data at the
  moment the trip is opened. `TripListViewModel` currently does not observe legs, so the `route_state`
  parameter may need data that is not immediately available. This should be explored during the propose
  phase to determine the best approach.
- **`is_first_trip` sampling moment** — the boolean is determined by checking whether the trip list was
  empty *before* the new trip was persisted. `TripListUiState.trips` is observed via a Flow from the
  repository, so the pre-creation count is the current list size at the time `ConfirmCreateTrip` is
  dispatched.
- **Possible split point:** if the Definition of Done runs long during refinement, the four coverage-gap
  fixes are separable from the taxonomy rewrite and can become their own story.

**`CountBand` must be a top-level type, not nested inside `AnalyticsEvent`.** It is used only by
`AnalyticsUserProperty` (for `trip_count_band`) and by no event, so nesting it under `AnalyticsEvent`
would put a vocabulary inside a type that never references it. That also rules out simply extending the
existing companion-object pattern, which is where the constants live today.

> An earlier draft of this plan had `trip_count_band` as **both** an event parameter on `trip_created`
> and a user property. That was dropped: same-named dimensions in different GA4 scopes are a mis-click
> waiting to happen, and the shared name concealed an undefined semantic — whether the band counted the
> trip being created. The event now carries `is_first_trip` instead. Do not reintroduce the overlap.

### Acceptance Criteria

1. **The 14 events in the tracking plan are implemented**, with exactly the names and parameters
   listed there.
2. **No event carries a raw identifier** — no `trip_id`, no `stop_id`, anywhere.
3. **No event carries free text** — no place names, no trip names, no search queries, no exception
   messages.
4. **No event carries coordinates.**
5. **`stop_set` is renamed `stop_added`** and reparameterised to `{ stop_type, stop_count }`.
6. **`operation_failed` carries `error_type`, not `error_message`**, where `error_type` is a bounded
   enum classified from the throwable by a dedicated, unit-tested classifier.
7. **Every failure path fires both channels** — `logEvent(OperationFailed(operation, errorType))` for
   the rate, and `trackException(throwable, operation)` for the stack trace. The event answers *how
   often*; the exception answers *where and why*. Neither substitutes for the other.
8. **The throwable is passed only to `trackException`** — never into an event parameter, and its message
   is never read into one.
9. **Every enumerated parameter value is produced from an enum's `value` property**, never from
   Kotlin's `.name`.
10. **`CountBand` is a top-level type**, usable by `AnalyticsUserProperty` without being nested inside
    `AnalyticsEvent`.
11. **No event parameter shares a name with a user property** — the two vocabularies are disjoint.
12. **`trip_created` carries `is_first_trip`**, defined as "the user had no trips before this one", so
    the sampling moment is unambiguous.
13. **All emitted values are `snake_case`.**
14. **The four coverage gaps emit events** — undo departure, place search failure, place detail failure,
    and navigation launch.
15. **The TODO at `TripDetailViewModel.kt:148` is resolved** — either implemented or removed with a
    recorded reason.
16. **Both user properties are set** — `trip_count_band` and `distance_unit` — via the
    `AnalyticsClient.setUserProperty(...)` API introduced by 9.1.1, with `AnalyticsUserProperty`
    subtypes carrying bounded values.
17. **`distance_unit` is set at app start**, before the first event is logged. User properties apply
    forward only, so a property set late leaves the session's earlier events unsegmentable.
18. **`trip_count_band` is updated whenever the count changes band** — on trip creation and on trip
    list load — not only once at start.
19. **Banding functions are unit-tested at their boundaries**, including zero and negative inputs.
20. **Every event in the code has a tracking-plan entry and vice versa** — verified by inspection.
21. **On-device verification** via `adb logcat -s Analytics`: each event fires exactly once per action,
    with expected parameters, and no identifier, free text, place name, or coordinate appears in any
    event payload. Both user properties are visible and distinguishable from events. On a forced failure,
    an `operation_failed` event **and** a tracked exception both appear, with the throwable's message
    present only on the exception line.

### Technical Notes

- **Sequencing matters.** Do this before 9.2.1. After a real backend ships, every rename becomes a
  breaking change to accumulated data.
- **Aggregate parameters need data the ViewModel may not have to hand.** `stop_count` after a removal,
  `leg_count` and banded totals on route calculation, `stop_position` for departures — check what is
  already in `TripDetailUiState` (which holds `legs`, `formattedTotalDistance`, and the stop lists)
  before adding new plumbing.
- **`distance_band` and `duration_band` should band the raw values**, not parse the formatted display
  strings. `Leg` carries the raw distance and duration; the formatters are for the UI.
- `distance_unit` is already derived by `DistanceFormatter` for imperial/metric display — reuse that
  determination rather than re-deriving it.
- Band boundaries in the tracking plan are a first guess at a road-trip distribution. They are cheap to
  change now and expensive once data accumulates, so prefer more bands over fewer.
- Conventions: `docs/guidelines/guidelines-analytics.md`.
- `core/analytics` is not Kover-excluded — every new enum, the classifier, and
  the banding functions need tests to clear the 95% bound.
- **Possible split point:** if the Definition of Done runs long during refinement, the four coverage-gap
  fixes are separable from the taxonomy rewrite and can become their own story.
