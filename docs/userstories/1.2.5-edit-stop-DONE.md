# 1.2.5 — Edit a Stop

**Epic:** Trip Management
**Feature:** Stop Management

## User Story

As a user, I want to edit a stop in my roadtrip so that I can correct or change a location.

## Description

The user can tap an existing stop and change its location. The stop's name and coordinates are updated while its order remains unchanged. This applies to any stop type: starting point, destination, or intermediate stops.

**Current state of the codebase:** Starting point and destination editing already works — tapping a filled card opens the `SetStopDialog` pre-populated with current values, and confirming calls the existing `upsertStartingPoint` / `upsertDestination` repository methods. The gap is **intermediate stops**: tapping an intermediate stop card currently does nothing because no edit intent, dialog, or update path is wired.

## Acceptance Criteria

1. The user can tap an existing stop to edit it.
2. Editing opens the stop dialog pre-populated with the current place name, latitude, and longitude.
3. The stop's name, latitude, and longitude are updated on confirm.
4. The stop's order remains unchanged.
5. Previously calculated legs involving this stop are invalidated (no-op for now — leg calculation is not yet implemented; see Epic 3).

## Technical Analysis

### What Already Works

- **Starting point**: Tap filled `StopSection` card -> `OnSetStartingPointClicked` -> dialog pre-populated -> `OnStartingPointConfirmed` -> `SetStopUseCase(STARTING_POINT)` -> `upsertStartingPoint` -> updates existing record via `StopDao.update()`.
- **Destination**: Same flow via `OnSetDestinationClicked` / `upsertDestination`.

Both paths qualify as "edit" behaviour and satisfy acceptance criteria 1-4 with no changes required.

### What Needs to Be Built (Intermediate Stops)

#### Data Layer

**`StopDao.kt`** — Add a query to retrieve a stop by its primary key:
```kotlin
@Query("SELECT * FROM stops WHERE id = :stopId LIMIT 1")
suspend fun getStopById(stopId: String): StopEntity?
```

**`StopRepository.kt`** — Add a new method to the interface:
```kotlin
suspend fun updateStop(
    stopId: String,
    placeName: String,
    latitude: Double,
    longitude: Double,
): Result<Stop>
```

**`StopRepositoryImpl.kt`** — Implement: fetch the existing entity by ID, copy with new `placeName`/`latitude`/`longitude` (preserving `id`, `tripId`, `order`, `status`), call `StopDao.update()`, return the domain model.

#### Domain Layer

**`EditStopUseCase.kt`** (new file in `domain/usecase/`) — Accepts `stopId`, `placeName`, `latitude`, `longitude`. Trims `placeName`, delegates to `stopRepository.updateStop()`. Returns `Result<Stop>`.

```kotlin
class EditStopUseCase @Inject constructor(
    private val stopRepository: StopRepository,
) {
    suspend operator fun invoke(
        stopId: String,
        placeName: String,
        latitude: Double,
        longitude: Double,
    ): Result<Stop> {
        val trimmedName = placeName.trim()
        return stopRepository.updateStop(stopId, trimmedName, latitude, longitude)
    }
}
```

#### UI Layer

**`TripDetailUiState.kt`** — Add fields:
```kotlin
val editingStop: Stop? = null,
val isEditStopDialogVisible: Boolean = false,
```

**`TripDetailUiIntent.kt`** — Add intents:
```kotlin
data class OnEditStopClicked(val stop: Stop) : TripDetailUiIntent()
data class OnEditStopConfirmed(
    val stopId: String,
    val placeName: String,
    val latitude: Double,
    val longitude: Double,
) : TripDetailUiIntent()
data object OnDismissEditStopDialog : TripDetailUiIntent()
```

**`TripDetailViewModel.kt`** — Inject `EditStopUseCase`. Handle the three new intents:
- `OnEditStopClicked` -> store `editingStop` in state, set `isEditStopDialogVisible = true`
- `OnEditStopConfirmed` -> call `EditStopUseCase`, dismiss dialog on success, emit `ShowError` on failure
- `OnDismissEditStopDialog` -> clear `editingStop`, set `isEditStopDialogVisible = false`

**`TripDetailScreen.kt`** — Wire intermediate stop `onSetStopClicked` to emit `OnEditStopClicked(stop)`. Add a new `SetStopDialog` block (guarded by `isEditStopDialogVisible`) with:
- Dialog title: new string resource for "Edit stop"
- Pre-populated with `editingStop?.placeName`, `latitude`, `longitude`
- Confirm emits `OnEditStopConfirmed(editingStop.id, ...)`

**`strings.xml`** — Add new string resources:
- `trip_detail_edit_stop_dialog_title` — "Edit stop"
- Reuse existing intermediate stop hint/error strings for place name, latitude, longitude fields

### Security

- No new security concerns. Input validation (blank place name, coordinate range) is handled by the existing `SetStopDialog` client-side validation.
- The `StopDao.update()` uses Room's parameterised queries — no SQL injection risk.

### Performance

- Single `SELECT` + single `UPDATE` per edit — negligible overhead.
- The reactive `observeByTripId` Flow automatically propagates the change to the UI.

### GDPR / Sensitive Information

- No personal data involved. Stop data (place names, coordinates) is user-generated content stored locally on-device in Room. No data leaves the device.

### Non-Functional Requirements

- **Offline-first**: Fully local operation, no network dependency.
- **Data integrity**: The update preserves the stop's `id`, `tripId`, `order`, and `status`. Only `placeName`, `latitude`, and `longitude` change.

### Leg Invalidation (Future)

Acceptance criterion 5 mentions invalidating legs. Leg calculation is not yet implemented (Epic 3). When it is, editing a stop should invalidate the arriving and departing legs. For now, this is a documented no-op.
