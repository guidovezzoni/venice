# 1.2.4 — Reorder Stops

**Epic:** Trip Management
**Feature:** Stop Management

## User Story

As a user, I want to reorder intermediate stops in my roadtrip so that I can adjust the sequence of my journey.

## Description

The user can change the position of intermediate stops using move-up / move-down icon buttons displayed next to each intermediate stop on the trip detail screen. The starting point (order 0) and destination (highest order) remain pinned at the first and last positions respectively and cannot be reordered.

Move-up/move-down buttons are preferred over drag-and-drop because the standard Compose `LazyColumn` does not natively support drag-and-drop reordering — it would require a third-party library (e.g. `sh.calvin.reorderable`) or significant custom gesture code. Buttons provide a simple, accessible, and reliable interaction at this stage. Drag-and-drop can be introduced in a future enhancement if needed.

When a stop is moved, the `order` field of the affected stops is swapped atomically in a Room `@Transaction`.

### Fields Updated

| Field | Entity | Description |
|-------|--------|-------------|
| `order` | `StopEntity` | The ordinal position of the stop within the trip. Swapped between the moved stop and its neighbour. |

## Acceptance Criteria

- Each intermediate stop shows a move-up button (unless it is the first intermediate stop) and a move-down button (unless it is the last intermediate stop).
- Tapping move-up swaps the stop with the one above; tapping move-down swaps with the one below.
- The starting point and destination cannot be moved and do not display reorder buttons.
- Reorder buttons are not shown when there are fewer than 2 intermediate stops.
- The stop list updates immediately after reordering (via the existing `Flow`-based observation).
- No data is lost during reorder; only the `order` field changes.

## Endpoints / APIs

No network endpoints required — this is a local-only operation using the Room database.

### DAO Methods (new)

| Method | Signature | SQL |
|--------|-----------|-----|
| `getStopByTripIdAndOrder` | `suspend fun getStopByTripIdAndOrder(tripId: String, order: Int): StopEntity?` | `SELECT * FROM stops WHERE tripId = :tripId AND \`order\` = :order LIMIT 1` |
| `updateStopOrder` | `suspend fun updateStopOrder(stopId: String, newOrder: Int)` | `UPDATE stops SET \`order\` = :newOrder WHERE id = :stopId` |

## Security Considerations

- **No concerns.** All operations are local (Room database). No user input beyond selecting which stop to move. Stop IDs are UUIDs generated server-side. No injection surface.

## Performance Considerations

- **Minimal impact.** Swapping two rows by primary key is O(1) in SQLite. The existing `Flow`-based observation automatically emits the new order, triggering a single recomposition of the `LazyColumn`.
- No full-list re-sort is needed — only two `UPDATE` statements per move.

## GDPR & Sensitive Information

- **No concerns.** Stop data (place names, coordinates) is already stored locally. Reordering does not introduce new personal data or change data retention behaviour.

## Other Non-Functional Requirements

- **Accessibility:** Move buttons must have content descriptions (`trip_detail_move_stop_up` / `trip_detail_move_stop_down`) for screen readers.
- **Atomicity:** The two `UPDATE` statements must run inside a transaction to prevent an inconsistent state if the app is killed mid-operation.

## Original User Story

### User Story

As a user, I want to reorder stops in my roadtrip so that I can adjust the sequence of my journey.

### Description

The user can change the order of intermediate stops via drag-and-drop or move-up/move-down actions. The starting point and destination remain fixed at the first and last positions respectively.

### Acceptance Criteria

- The user can reorder intermediate stops.
- The starting point (first) and destination (last) cannot be moved.
- The UI provides a clear drag-and-drop or reorder interaction.
- After reordering, previously calculated legs are invalidated.

### Technical Notes

- Reordering updates the `order` field on affected `Stop` records.
- Invalidating legs means clearing cached `Leg` data and showing a prompt to recalculate (see 3.1.1).
- Jetpack Compose has drag-and-drop support via `LazyColumn` reorderable modifiers or third-party libraries.
