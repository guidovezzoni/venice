# 1.2.1 — Set a Starting Point

**Epic:** Trip Management
**Feature:** Stop Management
**Status:** WIP
**Depends on:** 2.1.1 (Place Search — for production UX; data layer can be built independently)

## User Story

As a user, I want to set a starting point for my roadtrip so that the route calculation knows where I'm departing from.

## Functional Description

When the user opens a trip's detail screen, they see a dedicated **Starting Point** section. If no starting point has been set, a placeholder with a *Set starting point* call-to-action is shown. Tapping it triggers place search (Epic 2); once a place is selected its name and coordinates are saved as the stop with `order = 0`.

The starting point is visually distinct from regular stops (dedicated icon and label). The user can tap the starting point at any time to change it, which replaces the existing `order = 0` stop rather than adding a new one.

> **Scope note:** until user story 2.1.1 (Place Search) is implemented, a simple stub dialog with *Place name*, *Latitude*, and *Longitude* text fields is used to allow the full data layer to be exercised and tested end-to-end.

## Acceptance Criteria

1. The Starting Point section is visible in `TripDetailScreen`, below the trip title.
2. When no starting point exists a placeholder with a *Set starting point* button is shown.
3. Tapping *Set starting point* (or the existing starting point to change it) opens the stub dialog (name + lat + lng fields).
4. The starting point is saved with `order = 0`, `placeName`, `latitude`, `longitude`, and `status = PENDING`.
5. If a starting point already exists, confirming a new selection replaces it (upsert on `order = 0`).
6. The starting point is visually distinguished from future intermediate stops (e.g. `TripOrigin` icon, label "Start").
7. The starting point persists across app restarts (stored in Room).
8. Input is validated: place name must be non-blank; latitude in `[-90, 90]`; longitude in `[-180, 180]`. Inline errors shown on invalid input.

### Database migration — version 1 → 2

`AppDatabase` must be bumped to **version 2** and a migration supplied:

```kotlin
val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("""
            CREATE TABLE IF NOT EXISTS stops (
                id TEXT NOT NULL PRIMARY KEY,
                tripId TEXT NOT NULL,
                placeName TEXT NOT NULL,
                latitude REAL NOT NULL,
                longitude REAL NOT NULL,
                `order` INTEGER NOT NULL,
                status TEXT NOT NULL,
                FOREIGN KEY (tripId) REFERENCES trips(id) ON DELETE CASCADE
            )
        """.trimIndent())
        db.execSQL("CREATE INDEX IF NOT EXISTS index_stops_tripId ON stops (tripId)")
    }
}
```

Pass this migration to `Room.databaseBuilder(...).addMigrations(MIGRATION_1_2)`.

## Repository Interface

```kotlin
interface StopRepository {
    suspend fun upsertStartingPoint(
        tripId: String,
        placeName: String,
        latitude: Double,
        longitude: Double,
    ): Result<Stop>

    fun observeStopsForTrip(tripId: String): Flow<List<Stop>>
}
```

`upsertStartingPoint` logic:
- Query for an existing stop where `tripId = tripId AND order = 0`.
- If found → update `placeName`, `latitude`, `longitude` in place (preserve same `id`).
- If not found → insert new stop with a fresh `UUID`, `order = 0`, `status = PENDING`.

## Use Case

```kotlin
class SetStartingPointUseCase @Inject constructor(
    private val stopRepository: StopRepository,
) {
    suspend operator fun invoke(
        tripId: String,
        placeName: String,
        latitude: Double,
        longitude: Double,
    ): Result<Stop> =
        stopRepository.upsertStartingPoint(tripId, placeName.trim(), latitude, longitude)
}
```

## Non-Functional Considerations

### Security

- No sensitive credentials or tokens are involved.
- Input validation guards against malformed coordinates before persisting (`latitude ∈ [-90, 90]`, `longitude ∈ [-180, 180]`).
- All data is stored locally (SQLite); no network calls in this story.

### Performance

- `observeStopsForTrip` returns a `Flow`, providing reactive updates without polling.
- The `index_stops_tripId` index ensures efficient filtered queries even as stop count grows.
- The upsert performs at most 2 DAO operations (`getStartingPoint` + `insert`/`update`), both on the IO dispatcher via `Dispatchers.IO` (injected or Room's default executor).

### GDPR / Privacy

- Latitude and longitude constitute location data and are PII under GDPR Art. 4(1).
- In this story, data is stored **on-device only** (Room/SQLite) — no data leaves the device.
- If a future story adds cloud sync or backup, coordinates must be flagged as sensitive and handled accordingly (encryption at rest, explicit user consent).

### Accessibility

- The *Set starting point* button must have a `contentDescription` for screen readers.
- The stub dialog's text fields must have proper labels (`OutlinedTextField` with `label` parameter) rather than hint-only descriptions.

## Original User Story

### 1.2.1 — Set a Starting Point

**Epic:** Trip Management
**Feature:** Stop Management

#### User Story

As a user, I want to set a starting point for my roadtrip so that the route calculation knows where I'm departing from.

#### Description

The user designates a location as the first stop of the trip. The starting point is selected via place search (see Epic 2) and stored with its name and coordinates. A trip must have a starting point before a route can be calculated.

#### Acceptance Criteria

- The user can set a starting point via place search.
- The starting point is stored as the first stop (order = 0) with name, latitude, and longitude.
- The starting point is visually distinguished from intermediate stops in the UI.
- The starting point can be changed after initial selection.

#### Technical Notes

- **Data model:** `Stop(id, tripId, placeName, latitude, longitude, order, status)` — the starting point is simply the stop with `order = 0`.
- Depends on place search (2.1.1) for location selection.
- Store `latitude` and `longitude` on every stop from the start — this is critical for Level 2 (GPS-based ETA) where the Directions API is called with live coordinates as origin.
