# 8.1.1 — Spike: Offline+Online vs Online-Only

**Epic:** Cloud Sync & Multi-User
**Feature:** Backend Foundation & Auth

## User Story

As a developer, I want to analyse the tradeoffs between offline+online and online-only architectures so that we can make an informed decision before building the sync layer.

## Description

The app currently persists all data locally in a Room database. Before adding cloud sync via Supabase, we need to decide whether to keep Room as a local cache (offline+online) or replace it entirely with remote-first access (online-only). This story produces a decision document, not code.

## Acceptance Criteria

- A written analysis covers both approaches: offline+online (Room as cache, sync to Supabase) and online-only (Supabase as sole data source).
- The analysis addresses: data conflict resolution, implementation complexity, UX under poor connectivity, migration path from the current Room schema, and Supabase capabilities (Realtime, Row Level Security, offline SDK support).
- A clear recommendation is made with justification.
- The decision document is stored in `docs/improvements/` or an equivalent location.

## Technical Notes

- **Supabase offline:** The Supabase Kotlin SDK does not currently provide built-in offline persistence. An offline+online approach would require a custom sync layer on top of Room.
- **Conflict resolution:** If offline+online is chosen, a conflict strategy is needed (last-write-wins, merge, user prompt). This is non-trivial for ordered collections like stops.
- **Migration:** The current Room schema (trips + stops) maps naturally to Supabase tables, so the remote schema design is largely independent of this decision.
- This spike blocks all stories in Feature 8.2 (Trip Sync). Auth stories (8.1.3–8.1.6) can proceed independently.
