# 3.1.3 — See Estimated Duration for Each Leg

**Epic:** Route Calculation
**Feature:** Leg Calculation

## User Story

As a user, I want to see the estimated duration for each leg of the trip so that I can plan my time.

## Description

After route calculation (story 3.1.1), each leg already displays a compact summary between consecutive stops on the trip detail screen using the `LegSummary` composable. This composable currently shows both distance and duration, but the duration formatting is handled inside the composable itself via a private `@Composable` function (`formatDuration`). This violates the project convention that composables must be purely presentational with no logic.

This story refines the duration display to:
1. Extract duration formatting into a testable utility function (matching the pattern already established by `DistanceFormatter.kt`)
2. Pre-compute the formatted duration in the ViewModel and pass it to `LegSummary` as a string parameter (matching the `formattedDistance` pattern)
3. Ensure duration formatting handles edge cases correctly (zero duration, sub-minute durations, multi-hour durations)

Duration is formatted as hours and minutes in human-readable form:
- Sub-hour: "45 min"
- Multi-hour: "2h 15min"
- Zero or near-zero: "0 min" (when duration rounds to zero minutes)

### What already exists (delivered in 3.1.1)

- `Leg` domain model with `durationSeconds: Int` field
- `LegEntity` Room entity persisting duration in seconds
- `ObserveLegsUseCase` feeding legs to the ViewModel via Flow
- `TripDetailUiState.legs` holding leg data
- `LegSummary` composable rendering distance and duration between stops
- `formatDuration()` private `@Composable` function inside `LegSummary.kt` formatting seconds into hours/minutes
- String resources: `trip_detail_leg_duration_minutes` ("%1$d min"), `trip_detail_leg_duration_hours_minutes` ("%1$dh %2$dmin")
- `TripDetailScreen` rendering `LegSummary` and passing `formattedDistance` but not `formattedDuration`

### What this story adds

1. **Extracted duration formatting**: Move duration formatting from the composable into a dedicated testable utility function (following the same pattern as `DistanceFormatter.kt`)
2. **ViewModel pre-computation**: The ViewModel computes formatted durations and exposes them via `TripDetailUiState` (matching the `formattedLegDistances` pattern)
3. **Composable parameter change**: `LegSummary` receives `formattedDuration` as a string parameter instead of computing it internally
4. **Edge case handling**: Zero-second durations display as "0 min" rather than blank or undefined
5. **Full unit test coverage**: Duration formatting logic is fully testable without Compose test infrastructure

## Acceptance Criteria

1. Each leg between consecutive stops on the trip detail screen shows its estimated duration
2. Duration is formatted as minutes only (e.g. "45 min") when total duration is less than 60 minutes
3. Duration is formatted as hours and minutes (e.g. "2h 15min") when total duration is 60 minutes or more
4. Zero-second duration displays as "0 min"
5. Duration seconds are converted to minutes by integer division (truncation, not rounding) — e.g. 89 seconds displays as "1 min"
6. The duration label is read-only (no user interaction)
7. Duration formatting does not depend on locale (time units are universal in this context)
8. The `LegSummary` composable receives its formatted duration as a pre-computed string parameter (no formatting logic inside the composable)

## Security Considerations

- **No additional security concerns.** This story is a UI formatting refactoring. No new data is collected, transmitted, or stored. Duration data is already persisted locally from 3.1.1.
- **No API keys or credentials involved.** No network calls are made.
- **No user input processed.** The formatted values are derived entirely from stored numeric data.

## Performance Considerations

- **No performance concerns.** Duration formatting uses simple integer arithmetic (division and modulo). No database queries or network calls are added.
- **Pre-computation in ViewModel** avoids repeated formatting during recomposition — the formatted string is computed once when legs data changes and reused on every frame.
- **No additional memory allocation beyond existing pattern.** The `formattedLegDurations` map mirrors the existing `formattedLegDistances` map and has the same negligible footprint.

## GDPR and Sensitive Information

- **No GDPR concerns.** Duration of travel between geographic waypoints is not personal data.
- **No new data collection.** This story reads existing locally-stored duration values and formats them for display.
- **No data shared with third parties.** All processing is on-device.

## Non-Functional Requirements

- **Accessibility**: The duration text is part of the combined `Text` composable in `LegSummary`, which is accessible to screen readers by default. The formatted string (e.g. "2h 15min") is human-readable without additional content descriptions.
- **Internationalisation (i18n)**: Duration format strings are already defined as string resources in all three supported languages (EN, IT, ES). The formatting is locale-independent (no decimal separators or locale-specific number formatting needed for integer hours/minutes).
- **Backwards compatibility**: No database migration required. The `durationSeconds` field already exists in the `legs` table from the 3.1.1 migration.
- **Testability**: Moving formatting out of a `@Composable` function into a plain utility function allows unit testing with standard JUnit 4 + MockK (for Resources), without needing Compose test infrastructure.
- **Consistency**: After this story, both distance and duration follow the same architectural pattern: utility formatter -> ViewModel pre-computation -> composable receives pre-computed string. This eliminates the current inconsistency.

## Definition of Done

1. Duration is displayed for each leg on the trip detail screen using the `LegSummary` composable
2. Duration formatting follows the pattern: "X min" for sub-hour, "Xh Ymin" for 60+ minutes
3. Zero-second durations display as "0 min"
4. Duration formatting is extracted into a dedicated testable utility file under `ui/util/`
5. The ViewModel pre-computes formatted durations and exposes them via `TripDetailUiState.formattedLegDurations`
6. `LegSummary` composable receives `formattedDuration` as a parameter (no internal formatting logic)
7. Unit tests cover duration formatting for all edge cases (zero, sub-minute, sub-hour, multi-hour, boundary values)
8. Compose UI tests verify duration text is visible between stops
9. Preview coverage includes short-duration and long-duration variants (with the new parameter)
10. All existing tests continue to pass
11. App builds cleanly (`./gradlew check` passes)

## Original user story

### 3.1.3 — See Estimated Duration for Each Leg

**Epic:** Route Calculation
**Feature:** Leg Calculation

### User Story

As a user, I want to see the estimated duration for each leg of the trip so that I can plan my time.

### Description

After route calculation, each leg displays the estimated driving time between its two stops. Duration is shown in a human-readable format (e.g., "2h 15m").

### Acceptance Criteria

- Each leg in the trip view shows its estimated duration.
- Duration is formatted as hours and minutes (e.g., "2h 15m" or "45m" for sub-hour legs).
- If the route has not been calculated yet, duration is shown as unavailable (e.g., "---").
- Duration reflects typical driving conditions at the time of calculation (the API factors in average traffic by default).

### Technical Notes

- The Google Directions API returns duration in seconds (`legs[].duration.value`). Store as integer seconds in the database; format for display in the UI layer.
- The API also returns `duration_in_traffic` when a departure time is specified. For Level 1, the default `duration` (without traffic) is sufficient. Traffic-aware durations could be a future enhancement.
