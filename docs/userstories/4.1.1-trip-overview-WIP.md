# 4.1.1 — Trip Overview with Per-Leg Breakdowns

**Epic:** 4 — Trip Overview
**Feature:** 4.1 — Trip Summary View

## User Story

As a user, I want to see a trip overview with all stops and per-leg breakdowns so that I have a complete picture of my roadtrip at a glance.

---

## Refined Description

The Trip Overview is the central detail screen for a single trip — the hub from which the user reviews and drives their whole roadtrip. It presents, in one scrollable screen:

- the **trip name** in the header (currently a static "Trip Detail" placeholder is shown instead);
- the **ordered list of all stops**, from starting point through intermediate stops to destination;
- the **per-leg breakdown** (distance and duration) between each pair of consecutive stops;
- the **trip totals** (total distance and total estimated duration);
- the **progress status** of each stop (departed / current / upcoming) and a progress summary;
- a **clear prompt to calculate or recalculate the route** whenever the route is missing or out of date;
- **entry points** to the actions that mutate or act on the trip: add, edit, remove and reorder stops, and calculate/recalculate the route.

**Important scoping note — this is largely a consolidation story.** Most of the constituent pieces already exist on the current `TripDetailScreen`, delivered incrementally by earlier stories:

| Acceptance concern | Current status | Delivered by |
|--------------------|----------------|--------------|
| Ordered stop list (start → intermediate → destination) | Present | 1.2.x |
| Per-leg distance | Present (`LegSummary`) | 3.1.2 |
| Per-leg duration | Present (`LegSummary`) | 3.1.3 |
| Trip totals (distance + duration) | Present (`TripTotalSummary`) | 3.2.1 / 3.2.2 |
| Stop progress (departed/current/upcoming + summary) | Present (`StopSection`, `TripProgressSummary`) | 1.3.2 |
| Add / edit / remove / reorder stops entry points | Present | 1.2.x |
| Calculate route entry point | Present (button) | 3.1.1 |

The **new work** this story adds, therefore, is narrow and specific:

1. **Show the real trip name** in the header instead of the static placeholder string.
2. **Show a clear, explicit prompt** when the route has not been calculated or is out of date, so the user understands *why* legs/totals are unavailable and what to do about it (calculate / recalculate). Today the screen shows a generic "Calculate route" button plus an "unavailable" total, but no plain-language prompt tying the two together.

The remaining acceptance criteria are satisfied by verifying and, where needed, tidying the existing behaviour so the screen reads as one coherent "overview" rather than a stack of independently-built widgets.

### Out of scope (deferred, with rationale)

- **Navigate to a stop / navigate a leg.** The original story lists "navigate to a stop" as an entry point, but launching Google Maps navigation is Epic 5 (stories `5.1.1`, `5.1.2`), which are not yet done. This story should leave room for those entry points but must **not** implement navigation. See *Assumptions*.
- **Editing the trip name / trip metadata.** The UI sketch shows an `[Edit]` affordance next to the trip name. There is no existing "edit trip" story in the backlog (Trip CRUD covers create + list only). Renaming a trip is a separate concern and should be its own story; this story only *displays* the name. See *Assumptions*.

## Acceptance Criteria

Written as observable outcomes:

1. **Trip name displayed** — When the overview opens for a trip, the trip's actual name is shown in the header. If the name is momentarily unavailable (e.g. still loading), the header degrades gracefully to a neutral title rather than showing an empty or broken header.
2. **Ordered stop list** — All stops are listed in order from starting point to destination. Intermediate stops appear between them in their saved order.
3. **Per-leg breakdown** — Between each pair of consecutive stops, that leg's distance and duration are shown, using the locale-aware formatting already established (imperial/metric per device locale).
4. **Trip totals** — Total distance and total estimated duration are shown when the route is complete. When the route is not complete, a combined "trip totals unavailable" state is shown instead (existing behaviour).
5. **Progress status** — Each stop's status is visually indicated: departed, current, and upcoming are distinguishable, and a progress summary (e.g. "1 of 4 departed") is present.
6. **Recalculate prompt** — When the route has **not been calculated** or is **out of date relative to the current stops**, the screen shows a clear, plain-language prompt telling the user the route needs (re)calculating, alongside the calculate/recalculate action. When the route is present and current, no such prompt is shown.
7. **Calculate/recalculate action** — The user can trigger route calculation from the overview. While calculating, progress is indicated and the action is disabled to prevent re-triggering. On failure, an inline error is shown; on success, legs, totals and the prompt update accordingly.
8. **Stop action entry points** — From the overview the user can add a stop, edit a stop, remove a stop, and reorder intermediate stops, each via a clearly labelled control. (These already exist and must remain working after this story's changes.)
9. **Single coherent screen** — All of the above render within one scrollable screen without horizontal overflow, on the smallest supported screen width.

## Fields / State to be Updated

These describe *what data the screen must expose*, not how to compute or store it.

- **Trip name** — the overview state must carry the trip's display name so the header can render it. This requires the screen to observe the trip record for its `tripId` (the current ViewModel observes only stops and legs, not the trip itself).
- **Route freshness indicator** — the state must expose whether the route is missing / out of date versus present and current, so the UI can decide whether to show the recalculate prompt. This should be a pre-computed, display-ready signal (a boolean or small enum on the UI state), consistent with the guideline that composables contain no branching logic. It must stay in lockstep with the existing totals-availability logic (totals are already `null` when the route is incomplete).
- No new leg/stop/total fields are required — `legs`, `formattedLegDistances`, `formattedLegDurations`, `formattedTotalDistance`, `formattedTotalDuration`, `formattedStopCoordinates`, and `routeCalculationState` already exist on the state and are reused.

**Existing domain models are sufficient** and should not gain speculative fields:
- `Trip(id, name, createdAt, updatedAt, stopCount)`
- `Stop(id, tripId, placeName, latitude, longitude, order, status)`
- `Leg(id, tripId, fromStopId, toStopId, distanceMetres, durationSeconds, encodedPolyline)`

> Note: there is currently no persisted "stale" flag on `Leg`; route invalidation deletes legs outright on stop mutation. So in the current model "stale" collapses into "missing/incomplete legs". The recalculate prompt should therefore key off route completeness (do the persisted legs fully and correctly cover the current ordered stops), not off a dedicated stale flag. If a first-class staleness concept is later wanted, it is a separate modelling decision for the propose phase — do not invent a persisted flag speculatively.

---

## Endpoints

**No new external endpoints are introduced by this story.** It is a presentation/aggregation story over data the app already holds.

- Trip, stop, and leg data are read from **local persistence** (Room), observed as reactive streams. No network call is needed to render the overview.
- Route (re)calculation reuses the **existing** Google Directions API integration delivered in 3.1.1, via the existing calculate-route path. This story does not change the request/response contract, the API key handling, or the persistence of results.

## How to Create Unit Tests

Follow the project testing guidelines (JUnit 4, MockK, GIVEN/WHEN/THEN naming, `createViewModel(...)` factory with defaulted params, 95%+ coverage, one test file per new source class).

**ViewModel tests (`app/src/test/`)** — dispatch intents via `onIntent()` and assert on `uiState`:
- GIVEN a trip with a known name WHEN the overview loads THEN `uiState` exposes that trip name.
- GIVEN no legs persisted for a multi-stop trip WHEN state is observed THEN the route-needs-calculation signal is true and totals are unavailable.
- GIVEN legs fully covering the ordered stops WHEN state is observed THEN the signal is false and totals are available.
- GIVEN a stop is added/edited/removed/reordered (which invalidates legs) WHEN state re-emits THEN the signal flips back to "needs calculation".
- GIVEN calculate route succeeds/fails WHEN the calculate intent is dispatched THEN `routeCalculationState` transitions correctly and the signal updates on success — extend the existing calculate-route tests rather than duplicating setup.

**New use case test** — GIVEN a trip id present in the repository WHEN the use case is invoked THEN it returns the mapped domain `Trip`; GIVEN the id is absent THEN it surfaces the not-found outcome as a `Result` failure / null per the chosen contract.

**Repository impl test** — verify the single-trip read maps the entity to the domain model and does not leak data-layer types.

**Compose UI tests (`app/src/androidTest/`)** — extend the existing `TripDetailScreen` test:
- Trip name is displayed in the header.
- Recalculate prompt is shown when the state flags the route as needing calculation, and hidden when it does not.
- Existing coverage (stop list, legs, totals, progress, add/edit/remove/reorder intents, dialog visibility) continues to pass.

## Non-Functional Requirements

### Security
- **No new attack surface**: the overview reads local data and reuses the existing route path; it introduces no new endpoint, permission, or input field. The only new external-facing element is displaying the trip name, which is user-authored text — render it as text only (no HTML/markup interpretation) to avoid injection-style rendering issues.
- **API key**: unchanged; route calculation continues to use the existing key handling. Do not surface or log the key. Confirm no additional logging of request URLs is introduced.

### Performance
- The screen already aggregates three reactive streams (trip, stops, legs). Ensure the added trip observation does not introduce redundant recompositions or duplicate collection of the same stream — formatting and freshness computation should happen once in the ViewModel (composables stay presentational).
- Long trips (up to the existing 25-stop cap) must scroll smoothly; the list is already lazy. Avoid recomputing formatted strings on every recomposition — keep them pre-computed in state as now.
- The recalculate-freshness check runs on every stop/leg emission; it must be an O(n) comparison over stops/legs, not anything heavier.

### GDPR & Sensitive Information
- Trip names and stop place names/coordinates are **user-generated personal data** (they can reveal home addresses and travel patterns). This story only *displays* data already stored locally; it does not transmit anything new.
- Do **not** log the trip name, stop names, or coordinates (including in analytics event parameters or error logs). Analytics events for this screen should stay identifier-only, consistent with existing events (e.g. `ScreenViewed`, trip id only) — do not add place names or coordinates to any event.
- No new data is persisted or sent to any third party by this story. If/when cloud sync (Epic 8) lands, retention/erasure is handled there, not here.

### Accessibility & Other
- The trip name in the header and the recalculate prompt must have appropriate content descriptions / be readable by screen readers; the prompt must not rely on colour alone to convey "route out of date".
- Support light and dark themes and dynamic font scaling without clipping (the prompt copy must wrap, not truncate meaning).
- Maintain UK English base copy and use a real ellipsis character.
- No horizontal overflow at the smallest supported width.
