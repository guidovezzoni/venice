# 9.1.2 — Implement the Analytics Taxonomy and Close Coverage Gaps

**Epic:** Analytics
**Feature:** Analytics Foundation

## User Story

As a product owner, I want the app to emit a consistent, analysable set of events covering every user
action, so that once a real analytics backend is connected I can answer concrete questions about how
people plan road trips — rather than discovering the data is unusable.

## Description

The current 10-event taxonomy will not survive contact with a real analytics backend. Almost every
event carries a raw UUID (`trip_id`, `stop_id`), and high-cardinality parameters collapse into GA4's
`(other)` bucket while consuming the limited custom-dimension budget. `operation_failed` forwards
`error.message` verbatim, which is both unbounded cardinality and a live PII path — a Places or
Directions error can contain a place name the user typed. `stop_set` emits `stopType.name`, producing
`STARTING_POINT` in an otherwise `snake_case` dataset.

Several shipped features also emit nothing at all.

This story replaces the taxonomy with the 14 events defined in `docs/analytics/tracking-plan.md`, built
to answer four stated product questions: funnel completion, feature adoption, reliability, and trip
shape. Raw identifiers are replaced throughout by low-cardinality aggregates — `stop_count`,
`leg_count`, `stop_type`, banded distances and durations.

**Doing this now is deliberate and time-critical.** Nothing consumes these events yet, so renaming the
whole set costs nothing: no historical data, no dashboards, no funnels. That window closes permanently
the moment story 9.2.1 ships Firebase.

Depends on 9.1.1 (the renamed abstraction).

### Coverage gaps to close

| Location | Currently emits |

| `TripDetailViewModel` place detail failure (~line 323) | nothing |

| `TripDetailViewModel.kt:148` | a TODO deferring a total-duration event |

### Enumerated values become enums

Loose `String` constants in the `AnalyticsEvent` companion are replaced by enums, one type per file,
each carrying an explicit `value: String` in `snake_case`:

`AnalyticsScreen`, `AnalyticsOperation`, `AnalyticsErrorType`, `StopTypeParam`, `DistanceBand`,
`DurationBand`, `CountBand`.

Events emit `.value`, **never** `.name`. This is what structurally prevents the `STARTING_POINT`
casing bug from recurring — it makes the correct thing the only convenient thing.

## Acceptance Criteria

1. **The 14 events in the tracking plan are implemented**, with exactly the names and parameters
   listed there.
2. **No event carries a raw identifier** — no `trip_id`, no `stop_id`, anywhere.
3. **No event carries free text** — no place names, no trip names, no search queries, no exception
   messages.
4. **No event carries coordinates.**
5. **`stop_set` is renamed `stop_added`** and reparameterised to `{ stop_type, stop_count }`.
6. **`operation_failed` carries `error_type`, not `error_message`**, where `error_type` is a bounded
   enum classified from the throwable by a dedicated, unit-tested classifier.
7. **Every enumerated parameter value is produced from an enum's `value` property**, never from
   Kotlin's `.name`.
8. **All emitted values are `snake_case`.**
9. **The four coverage gaps emit events** — undo departure, place search failure, place detail failure,
   and navigation launch.
10. **The TODO at `TripDetailViewModel.kt:148` is resolved** — either implemented or removed with a
    recorded reason.
11. **Both user properties are set** — `trip_count_band` and `distance_unit` — via the
    `AnalyticsClient.setUserProperty(...)` API introduced by 9.1.1, with `AnalyticsUserProperty`
    subtypes carrying bounded values.
12. **`distance_unit` is set at app start**, before the first event is logged. User properties apply
    forward only, so a property set late leaves the session's earlier events unsegmentable.
13. **`trip_count_band` is updated whenever the count changes band** — on trip creation and on trip
    list load — not only once at start.
14. **Banding functions are unit-tested at their boundaries**, including zero and negative inputs.
15. **Every event in the code has a tracking-plan entry and vice versa** — verified by inspection.
16. **On-device verification** via `adb logcat -s Analytics`: each event fires exactly once per action,
    with expected parameters, and no identifier, free text, place name, or coordinate appears in any
    payload. Both user properties are visible in the log, distinguishable from events.

## Analytics

This story *is* the analytics definition. The authoritative specification is
`docs/analytics/tracking-plan.md` — the event dictionary, the parameter reference with allowed values,
the user properties, and the legacy migration table. It should not be duplicated here; refinement
should read it rather than restate it.

Scope boundary: `screen_viewed` keeps its current ViewModel-`init` trigger in this story. Moving it to
navigation-driven firing is story 9.1.3, so the two changes stay separately reviewable.

## Technical Notes

- **Sequencing matters.** Do this before 9.2.1. After a real backend ships, every rename becomes a
  breaking change to accumulated data.
- **Aggregate parameters need data the ViewModel may not have to hand.** `stop_count` after a removal,
  `leg_count` and banded totals on route calculation, `stop_position` for departures — check what is
  already in `TripDetailUiState` (which holds `legs`, `formattedTotalDistance`, and the stop lists)
  before adding new plumbing.
- **`distance_band` and `duration_band` should band the raw values**, not parse the formatted display
  strings. `Leg` carries the raw distance and duration; the formatters are for the UI.
- `distance_unit` is already derived by `DistanceFormatter` for imperial/metric display — reuse that
  determination rather than re-deriving it.
- Band boundaries in the tracking plan are a first guess at a road-trip distribution. They are cheap to
  change now and expensive once data accumulates, so prefer more bands over fewer.
- Conventions: `docs/guidelines/guidelines-analytics.md`.
- `domain/analytics` and `data/analytics` are not Kover-excluded — every new enum, the classifier, and
  the banding functions need tests to clear the 95% bound.
- **Possible split point:** if the Definition of Done runs long during refinement, the four coverage-gap
  fixes are separable from the taxonomy rewrite and can become their own story.
