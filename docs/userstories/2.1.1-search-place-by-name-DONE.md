# 2.1.1 — Search for a Place by Name

**Epic:** Place Search
**Feature:** Geocoding

## User Story

As a user, I want to search for a place by name when adding or editing a stop so that I don't have to know exact coordinates.

## Description

When adding or editing a stop, the user types a place name (city, address, landmark) into the existing "Place name" field and sees a list of matching autocomplete suggestions below it. They select a suggestion, and its name, latitude, and longitude are automatically populated — the manual latitude/longitude fields become read-only once a place is selected. This replaces the current workflow where users must manually enter coordinates.

The Google Places Autocomplete (New) API is used for suggestions. A session token groups the autocomplete requests and the subsequent Place Details call into a single billing session (~$0.017/session).

## Acceptance Criteria

1. **Search field integration**: The existing "Place name" `OutlinedTextField` in `SetStopDialog` doubles as the search input. As the user types, autocomplete suggestions appear below it.
2. **Debounced requests**: API calls are debounced (300 ms) to avoid excessive network traffic while typing.
3. **Suggestion list**: Each suggestion shows the place name (primary text) and a disambiguating detail such as region or country (secondary text).
4. **Selection**: When the user taps a suggestion, the place name field is updated and the latitude/longitude fields are auto-populated from the Place Details response. The suggestion list is dismissed.
5. **Coordinates become read-only**: After a place is selected via autocomplete, the latitude and longitude fields are displayed as read-only. If the user clears or changes the place name text, the fields revert to editable (or the coordinates are cleared).
6. **Manual fallback**: The user can still manually type a place name and coordinates if autocomplete is not used or no suggestion is selected. This preserves backward compatibility.
7. **Edit mode pre-population**: When editing an existing stop, the dialog opens with the existing place name and coordinates pre-populated, as it does today. The user can search for a new place to replace them.
8. **Error handling**: Network errors or empty results show a brief inline message (e.g. "No results found" or "Search unavailable") — they do not block the user from manually entering data.
9. **Loading indicator**: A small progress indicator is shown while autocomplete results are being fetched.
10. **Session token lifecycle**: A session token is created when the dialog opens and expires when a place is selected or the dialog is dismissed, ensuring correct billing.

## Detailed Technical Specification

### 1. Dependencies to Add

Add to `gradle/libs.versions.toml`:

```toml
[versions]
playServicesPlaces = "4.2.0"  # Google Places SDK (New)

[libraries]
google-places = { group = "com.google.android.libraries.places", name = "places", version.ref = "playServicesPlaces" }
```

Add to `app/build.gradle.kts`:

```kotlin
implementation(libs.google.places)
```

### 2. API Key Configuration

- Obtain a Google Maps Platform API key with Places API (New) enabled from the Google Cloud Console.
- Store the key in `local.properties` as `MAPS_API_KEY=<key>` (this file is already gitignored).
- Surface the key via `BuildConfig`:
  - In `app/build.gradle.kts`, read `local.properties` and add `buildConfigField("String", "MAPS_API_KEY", "\"${mapsApiKey}\"")`.
  - Enable `buildFeatures.buildConfig = true` if not already enabled.
- Initialise the Places SDK in `Application.onCreate()` or via a Hilt provider using `Places.initializeWithNewPlacesApiEnabled(context, BuildConfig.MAPS_API_KEY)`.

### 3. New Domain Models

```kotlin

```

Create `PlaceDetail` in `domain/model/`:

```kotlin
data class PlaceDetail(
    val name: String,
    val latitude: Double,
    val longitude: Double,
)
```

### 4. Domain Layer — Repository Interface

Create `PlaceSearchRepository` in `domain/repository/`:

```kotlin
interface PlaceSearchRepository {
    suspend fun getAutocompleteSuggestions(
        query: String,
        sessionToken: Any,
    ): Result<List<PlaceSuggestion>>

    suspend fun getPlaceDetails(
        placeId: String,
        sessionToken: Any,
    ): Result<PlaceDetail>
}
```

Note: `sessionToken` is typed as `Any` at the domain boundary to avoid leaking the Places SDK type into the domain layer. The data layer casts it to `AutocompleteSessionToken`.

### 5. Data Layer — Repository Implementation

Create `PlaceSearchRepositoryImpl` in `data/repository/`:

- Uses `PlacesClient.findAutocompletePredictions()` for suggestions.
- Uses `PlacesClient.fetchPlace()` for details (fetching `Place.Field.DISPLAY_NAME` and `Place.Field.LOCATION`).
- Maps SDK responses to domain models via mappers.
- Handles exceptions and returns `Result.failure()` on errors.

### 6. Data Layer — Mappers

Create `PlaceSuggestionMapper` in `data/mapper/` to convert `AutocompletePrediction` → `PlaceSuggestion`.

Create `PlaceDetailMapper` in `data/mapper/` to convert `Place` → `PlaceDetail`.

### 7. DI Module

Create `PlacesModule` in `di/`:

- Provides `PlacesClient` singleton via `Places.createClient(context)`.
- Binds `PlaceSearchRepositoryImpl` to `PlaceSearchRepository`.

### 8. Domain Layer — Use Cases

Create `SearchPlacesUseCase` in `domain/usecase/`:

```kotlin
class SearchPlacesUseCase @Inject constructor(
    private val placeSearchRepository: PlaceSearchRepository,

    suspend operator fun invoke(
        query: String,

```

Create `GetPlaceDetailUseCase` in `domain/usecase/`:


### 9. UI Layer Changes

#### `SetStopDialog` composable changes

- Add new parameters for search state: `suggestions: List<PlaceSuggestion>`, `isSearching: Boolean`, `searchError: String?`.
- Add new intent callbacks: `onSearchQueryChanged: (String) -> Unit`, `onSuggestionSelected: (PlaceSuggestion) -> Unit`.
- Below the place name `OutlinedTextField`, render a `LazyColumn` (or `Column`) of suggestion items when `suggestions` is not empty.
- Show a small `CircularProgressIndicator` inside or near the text field while `isSearching` is true.
- When a suggestion is tapped, call `onSuggestionSelected`.
- When coordinates are auto-populated (non-blank and sourced from autocomplete), make the latitude/longitude fields read-only (`enabled = false` or `readOnly = true`).

#### `TripDetailUiState` changes

Add fields:

```kotlin
val placeSuggestions: List<PlaceSuggestion> = emptyList(),
val isSearchingPlaces: Boolean = false,
val searchError: String? = null,
```

#### `TripDetailUiIntent` changes

Add intents:

```kotlin
data class OnSearchQueryChanged(val query: String) : TripDetailUiIntent()
data class OnSuggestionSelected(val suggestion: PlaceSuggestion) : TripDetailUiIntent()
```

#### `TripDetailViewModel` changes

- Inject `SearchPlacesUseCase` and `GetPlaceDetailUseCase`.
- Manage an `AutocompleteSessionToken` (created when a dialog opens, cleared on selection or dismiss).
- On `OnSearchQueryChanged`: debounce 300 ms, then call `SearchPlacesUseCase`, update `placeSuggestions` in state.
- On `OnSuggestionSelected`: call `GetPlaceDetailUseCase`, update the dialog fields with the returned name/latitude/longitude, clear suggestions, clear the session token.
- On dialog dismiss intents: clear suggestions, clear the session token.

### 15. Security Considerations

- **API key exposure**: The API key is stored in `local.properties` (gitignored) and surfaced via `BuildConfig`. It should be restricted in the Google Cloud Console to the app's package name and SHA-1 signing certificate. It must never be committed to version control.
- **Input sanitisation**: User search queries are passed directly to the Places SDK, which handles sanitisation. No raw SQL or HTTP construction is involved.
- **No user data sent**: Only the search query string is sent to Google. No PII, trip data, or account information is transmitted.

### 16. Performance Considerations

- **Debouncing**: 300 ms debounce on search input prevents excessive API calls.
- **Session tokens**: Grouping autocomplete + details into a session reduces cost and avoids redundant network calls.
- **Lazy suggestion list**: Using `LazyColumn` for suggestions ensures efficient rendering even with many results (though Google typically returns 5).
- **Coroutine cancellation**: Previous search coroutines are cancelled when a new query arrives (using `Job` cancellation or `MutableStateFlow` + `collectLatest`).

### 17. GDPR & Sensitive Information

- No personal data is collected or stored beyond the place name and coordinates the user explicitly selects.
- Google Places API usage is subject to Google's Terms of Service and Privacy Policy. The app does not store or forward Google's place IDs beyond the current session.
- No analytics or tracking is added as part of this story.

### 18. Other Non-Functional Requirements

- **Offline behaviour**: If the device is offline, autocomplete will fail gracefully — the error message is shown and the user can still enter data manually.
- **Accessibility**: Suggestion items should be focusable and have content descriptions. The search field should announce loading state to screen readers.
- **Internationalisation**: All new user-facing strings are extracted to `strings.xml`. The Places API returns localised results based on the device locale.

## Original User Story

### User Story

As a user, I want to search for a place by name when adding a stop so that I don't have to know exact coordinates.

### Description

When adding or editing a stop, the user types a place name (city, address, landmark) and sees a list of matching results. They select one, and its name and coordinates are used for the stop. This is the primary way users will input locations.

### Acceptance Criteria

- A search field is presented when adding or editing a stop.
- As the user types, matching places are suggested (autocomplete).
- Each suggestion shows the place name and a disambiguating detail (e.g., region, country).
- The user selects a suggestion to confirm the place.
- The selected place's name, latitude, and longitude are stored on the stop.

### Technical Notes

- **API:** Google Places Autocomplete (part of the Google Maps Platform). Returns place predictions as the user types, with minimal API calls via debouncing.
- **Pricing:** Places Autocomplete is billed per session (not per keystroke) when using session tokens — roughly $0.017 per session. Well within the $200/month free credit during development.
- **Alternative:** Google Geocoding API is simpler (single request, no autocomplete) but worse UX. Autocomplete is strongly recommended.
- This is a cross-cutting dependency — stories 1.2.1, 1.2.2, 1.2.3, and 1.2.5 all rely on this.
