# 9.3.1 — Ask for Consent Before Collecting Analytics

**Epic:** Analytics
**Feature:** Analytics Privacy

## User Story

As a user, I want to decide whether the app collects analytics about my usage, and to change my mind
later, so that I stay in control of data about me.

## Description

Stories 9.1 and 9.2 ship analytics on the **assumption that consent is granted**. That assumption is
recorded in `docs/guidelines/guidelines-analytics.md` and is temporary. This story replaces it with an
actual consent mechanism.

The assumption was defensible rather than correct. It rests on two things: events carry no personal data
by design — no identifiers, no free text, no coordinates — and
`docs/publishing/Privacy Policy.md` already discloses analytics SDK use, including that consent will be
obtained "where required by applicable law". Venice ships with Italian and Spanish localisations, so EU
users are squarely in scope, and that disclosure is a promise this story keeps.

Two facts make this a real story rather than a switch:

- **Venice has no settings screen.** There is nowhere for a consent toggle to live. This story either
  creates one or depends on a Settings epic being scheduled first. This is the main reason it is
  deferred rather than bundled into 9.2.1.
- **Both SDKs start collecting at process start.** Firebase Analytics self-initialises through a
  `ContentProvider`, and Crashlytics collection is on by default. Consent state must therefore be
  applied before or during initialisation — checking it at the first `logEvent` call is too late.
  Regulators specifically test for SDKs firing before the consent surface is answered.

The consent decision is a product decision, deliberately left open here rather than pre-empted:
opt-in (nothing collected until the user agrees) is the strictest and best matches the existing
privacy-policy language, while opt-out (on by default, disableable) gives better data quality at higher
regulatory risk. Refinement should settle it explicitly.

Depends on 9.2.1 and 9.2.2 — there is nothing to gate until a real backend exists.

## Acceptance Criteria

*(To be completed at refinement, once the consent model and the settings-screen dependency are
settled. The following are the requirements known now.)*

1. **A consent model is chosen and recorded** — opt-in or opt-out — with the reasoning captured in
   `guidelines-analytics.md`, replacing the "assumed granted" position.
2. **No provider receives an event before consent is resolved** — enforced centrally over the provider
   set, not by each provider checking independently.
3. **User properties are gated on the same decision as events.** A user property is a persistent
   attribute attached to every subsequent event, so leaving properties ungated while blocking events
   would keep setting device-scoped attributes for a user who declined. Withdrawing consent must also
   clear or stop refreshing them.
4. **The exception channel's consent treatment is an explicit decision, not an oversight.**
   `trackException` carries stack traces to crash reporting — a different purpose from product
   analytics, and one many apps treat under a separate legal basis. Refinement must decide whether it
   shares the analytics decision or gets its own, and record the reasoning. What is not acceptable is
   leaving it ungated by default simply because it was not considered.
5. **Consent state is persisted** across app restarts and process death.
6. **The user can change the decision at any time**, not only on first run.
7. **Withdrawing consent takes effect immediately** — collection stops without requiring a restart.
8. **Firebase consent is propagated** via `setConsent(ANALYTICS_STORAGE, …)`, not only by dropping
   events client-side.
9. **Crashlytics collection follows the same decision** via `setCrashlyticsCollectionEnabled`, set early
   enough to take effect.
10. **No event is emitted before the user has interacted with the consent surface** on first run.
11. **The privacy policy matches the implemented behaviour** — verified by reading both.
12. **The Play Data Safety declaration is reviewed** against the consent behaviour.
13. **Debug builds are unaffected** in a way that would mask a consent bug — the Logcat provider must
    respect consent too, or its exemption must be a recorded decision.

## Analytics

No new events. This story gates the delivery of every existing event.

**Deliberately not tracked:** the consent decision itself. Recording whether a user consented is
processing data about a privacy choice, in a system they may have just opted out of. If a consent-rate
metric is ever wanted, it needs its own explicit decision and probably a different mechanism.

## Technical Notes

- **Blocked on the absence of a settings screen.** Resolve that dependency before scheduling: either
  this story grows to include a minimal settings screen, or a Settings epic comes first. Refinement
  should not paper over this.
- A decorator over the provider set is the natural shape — it keeps the check in one place and satisfies
  the "no provider receives an event before consent is resolved" criterion structurally. Individual
  providers checking consent is the version that eventually leaks.
- Persistence: DataStore is the conventional choice. Room already exists in the project, but consent is
  a single preference rather than relational data.
- The "no event before the consent surface is answered" criterion is the one that fails silently and
  matters most. Verify it by watching network traffic or Logcat from a cold start on a fresh install —
  not by reading the code.
- Timing constraint: `setConsent` and `setCrashlyticsCollectionEnabled` must be applied early. Investigate
  whether Firebase's manifest-level default-off metadata is needed to satisfy that same criterion, since
  the `ContentProvider` initialises before any application code runs.
- **Provider initialisation is currently an unnamed step, and this story is where it stops being
  optional.** The abstraction has no initialisation hook: providers are constructed by Hilt and Firebase
  self-initialises via `ContentProvider`, so nothing in the design says *when* a provider becomes live.
  Consent inverts that — the decision has to be applied before or during SDK init, so the ordering must
  become explicit. Refinement should decide whether that means an `initialise()` step on
  `AnalyticsProvider`, manifest-level defaults, or a consent-aware factory. Prefer whichever avoids
  passing `Application` into a provider — that Android coupling is what the existing
  `TripDetailViewModel` TODO already complains about.

  This is **confirmed, not speculative**: PostHog's Android SDK holds an `enabled` flag that starts
  `false` and is only set by `setup(config)`, so *every* call before setup is a silent no-op — events are
  dropped with nothing but a log line. Firebase and Crashlytics have the opposite problem, starting
  collection before application code runs. A design with no named initialisation point gets both failure
  modes: silently lost events on one backend, ungated collection on another. If a third destination
  (Amplitude, PostHog) is ever added, this becomes the first thing that must be solved.
- Consider whether consent should also gate the `AD_ID` permission introduced by the Firebase manifest
  merge in 9.2.1.
- Conventions and the current assumed-consent position: `docs/guidelines/guidelines-analytics.md`.
