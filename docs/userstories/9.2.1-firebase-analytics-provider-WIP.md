# 9.2.1 — Send Events to Firebase Analytics

**Epic:** 9 - Analytics
**Feature:** 9.2 - Analytics Destinations
**Depends on:** 9.1.2 (analytics taxonomy and coverage)

## User Story

As a product owner, I want events delivered to Firebase Analytics, so that I can actually see how the
app is used instead of relying on Logcat on my own device.

## Description

Events currently reach only a Logcat sink in debug builds. Release builds have zero providers
registered, making every analytics operation a silent no-op. This story adds the first real analytics
destination by integrating Firebase Analytics as a new `AnalyticsProvider`.

The analytics abstraction from story 9.1.1 already provides the extension point: a new
`FirebaseAnalyticsProvider` implementing `AnalyticsProvider` and registered via `@Binds @IntoSet` in
the `main` source set (not `debug`) is all that is structurally required. The provider owns every
Firebase-specific concern -- `Bundle` mapping, event-name translation, platform naming and size limits
-- so no other layer becomes aware that Firebase exists. That containment is the whole point of the
abstraction and must not be eroded by letting Firebase types leak upward.

Firebase Analytics is free with unlimited event volume. DebugView provides near-real-time on-device
verification of actual payloads, which matters because a taxonomy is only as good as what actually
arrives at the backend.

### What this story delivers

- All 14 tracking-plan events (`docs/analytics/tracking-plan.md`) reaching Firebase Analytics
- Both user properties (`trip_count_band`, `distance_unit`) forwarded to Firebase
- `screen_viewed` mapped to Firebase's built-in `SCREEN_VIEW` event so it populates the standard
  screen reports rather than sitting as an unrelated custom event
- Firebase's automatic event collection reviewed and explicitly controlled
- `trackException` is a no-op in this provider -- crash reporting is handled by Crashlytics in
  story 9.2.2 via a separate provider
- Platform limits (name lengths, value lengths, reserved prefixes, parameter counts) enforced within
  the provider, with violations surfaced loudly in debug builds

### What this story does NOT deliver

- Crash reporting (story 9.2.2, Crashlytics)
- User consent gate (story 9.3.1) -- consent is assumed granted for now (see GDPR section)
- Screen-view tracking from navigation (story 9.1.3) -- this story delivers the destination; 9.1.3
  delivers the correct trigger
- CI/CD pipeline (tracked separately in `docs/improvements/github-ci-setup.md`) -- but the build
  must not break when `google-services.json` is absent

## Acceptance Criteria

### Dependency and build setup

1. **Dependencies added via the version catalog** -- `firebase-bom`, `firebase-analytics`, and the
   `google-services` plugin are declared in `gradle/libs.versions.toml`. No hardcoded version strings
   anywhere.
2. **`google-services.json` is gitignored** and sourced the same way as `MAPS_API_KEY` (via
   `local.properties` or equivalent local mechanism), with a documented fallback when absent.
3. **A build without `google-services.json` does not fail with a confusing plugin error.** The build
   either succeeds (if a dummy config or plugin guard is used) or fails with a clear, actionable error
   message explaining what is missing and where to obtain it.
4. **Both debug and release variants build successfully** -- `./gradlew assembleDebug assembleRelease`.
5. **The `google()` repository filter in `settings.gradle.kts`** is confirmed to resolve Firebase
   artifacts. The current filter uses `includeGroupByRegex("com\\.google.*")` -- Firebase artifacts
   are under `com.google.firebase` and should match, but this must be verified rather than assumed.

### Provider implementation

6. **`FirebaseAnalyticsProvider` implements `AnalyticsProvider`** and maps each `AnalyticsEvent`
   subclass to a Firebase `Bundle`, using the event's `name` and `properties`.
7. **Registered via a single `@Binds @IntoSet`** in the `main` source set's `AnalyticsModule`, with
   no other wiring changes. This is the story that gives release builds a destination for the first
   time.
8. **No Firebase type appears outside `core/analytics/` and `di/`.**
9. **`screen_viewed` maps to Firebase's built-in `SCREEN_VIEW`** event (using
   `FirebaseAnalytics.Event.SCREEN_VIEW`) with the `screen_name` parameter mapped to
   `FirebaseAnalytics.Param.SCREEN_NAME`. This populates the built-in screen reports rather than
   creating an unrelated custom event.
10. **`trackException` is a no-op** -- Firebase Analytics is a product analytics provider, not a crash
    reporter. The `trackException` channel is reserved for Crashlytics (story 9.2.2).
11. **The provider is thread-safe** -- `logEvent` and `setUserProperty` may be called from any thread
    or coroutine context.

### Automatic event collection

12. **Firebase's automatic `screen_view` collection is disabled** via the
    `google_analytics_automatic_screen_reporting_enabled` manifest meta-data tag set to `false`. Leaving
    both active double-counts screen views and corrupts any funnel that story 9.1.3 builds.
13. **Every other automatically-collected event is reviewed**, and any left enabled is a recorded
    decision with a tracking-plan entry. An automatic event that reaches the backend without appearing
    in the plan violates the plan's "every event has an entry" rule and is invisible to code review.
    The review outcome is documented in the change proposal.

### Platform limits

14. **Platform limits are enforced within the provider:**
    - Event names: max 40 characters, alphanumeric + underscores, must start with an alphabetic
      character, no reserved prefixes (`firebase_`, `google_`, `ga_`)
    - Parameter names: max 40 characters, same character rules, same reserved prefixes
    - String parameter values: max 100 characters
    - Max 25 parameters per event
    - A violation must surface loudly in debug builds (assertion or logged error) rather than being
      silently dropped. The exact mechanism is a design decision for the proposal phase.

### User properties

15. **Both user properties are forwarded** to `FirebaseAnalytics.setUserProperty`:
    - `trip_count_band` with values from `CountBand.value`
    - `distance_unit` with values from `DistanceUnitParam.value`
16. **User property names** follow the same platform limits as parameter names (max 24 characters for
    user properties, no reserved prefixes).

### Boolean parameter handling

17. **`is_first_trip` (Boolean) is sent as a String** (`"true"` / `"false"`) so it can be registered
    as a custom dimension in GA4. Firebase `Bundle` does accept Boolean, but GA4 custom definitions
    only support String and Numeric types. Sending it as Boolean would make it unregistrable as a
    dimension and invisible in reports. This decision is recorded in the tracking plan's parameter
    reference once confirmed.

### Custom definitions registration

18. **All custom event parameters and user properties from the tracking plan are registered** in the
    Firebase console under *Analytics > Custom Definitions*:
    - String parameters registered as custom **dimensions**
    - Numeric parameters (`stop_count`, `stop_position`, `leg_count`, `suggestion_count`,
      `suggestion_position`) registered as custom **metrics**
    - `is_first_trip` registered as a custom **dimension** (sent as String per AC 17)
    - Both user properties registered under *User Properties*
    - Unregistered definitions are accepted silently by the SDK but never appear in reports -- which
      is indistinguishable from a broken integration.

### Advertising ID

19. **The `AD_ID` permission added by Firebase's manifest merge is explicitly removed** if the app
    does not need advertising features. Firebase Analytics functions without the advertising ID; it
    falls back to the app instance ID. Removing it simplifies the Play Data Safety declaration and
    avoids collecting data the app has no use for.

### On-device verification

20. **DebugView verification**: with
    `adb shell setprop debug.firebase.analytics.app com.guidovezzoni.venice.debug`, exercise the full
    activation funnel and confirm:
    - Every event arrives with the expected name and parameters
    - Parameters are correctly typed (String dimensions, numeric metrics)
    - No `(other)` bucketing appears (would indicate unregistered custom definitions)
    - No missing parameters
    - Both user properties are attached to events logged after they are set
    - `screen_viewed` appears as the built-in `screen_view` event, not as a custom event
    - No duplicate automatic `screen_view` events appear
    - No unexpected automatic events appear that are not in the tracking plan
21. **A release build emits events to Firebase** -- confirm that a release-signed build logs events
    (this is the first release build to have an analytics destination).

### Compliance review

22. **Play Data Safety form is reviewed** against what the Firebase Analytics SDK actually collects
    and the AD_ID decision from AC 19.
23. **Privacy policy (`docs/publishing/Privacy Policy.md`) is reviewed** to ensure it covers Firebase
    Analytics data collection, US data processing, and the international transfer mechanisms already
    declared.

### CI compatibility

24. **CI can build without a committed `google-services.json`** -- the approach from AC 3 must not
    break the existing CI plan in `docs/improvements/github-ci-setup.md`. When CI is eventually set
    up, it must be possible to supply the config file as a secret.

## Security

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **`google-services.json` committed to git** | High | Add to `.gitignore` before the file is ever created in the working tree. The file contains Firebase API keys and project IDs. While Firebase security rules limit what can be done with these keys, they should not be public. |
| **API keys in `google-services.json`** | Medium | Firebase API keys are restricted by project-level security rules and are not secrets in the traditional sense (they are embedded in every distributed APK). However, committing them to a public repo exposes the project ID and enables abuse of unrestricted APIs. The gitignore entry and CI secret approach mitigate this. |
| **ProGuard/R8 stripping** | Low | Verify release builds work correctly with minification enabled. Firebase typically ships consumer ProGuard rules, but the release build must be tested end-to-end. |
| **Debug provider in release** | None (already mitigated) | The `DebugAnalyticsProvider` binding is already confined to `app/src/debug/`. The new `FirebaseAnalyticsProvider` binding goes in `main`, which is correct -- it should be available in all build variants. |

## Performance

| Concern | Impact | Mitigation |
|---------|--------|------------|
| **SDK initialisation time** | Low | Firebase Analytics self-initialises through a `ContentProvider`, adding a small amount of time to cold start. This is a fixed cost shared by all Firebase SDKs and is not configurable. Do not add explicit initialisation in `VeniceApplication.onCreate`. |
| **Event batching and network** | Negligible | Firebase batches events and uploads approximately every hour (or every 1,000 events, whichever comes first). Events are stored locally and uploaded in the background. No synchronous network calls occur on the event-logging path. |
| **APK size increase** | Low | Firebase Analytics adds approximately 200-400 KB to the APK after minification. Acceptable for the value delivered. |
| **Battery and data usage** | Negligible | Background uploads are batched and infrequent. Firebase Analytics is designed for always-on collection with minimal battery impact. |

### Technical Notes

- Firebase Analytics self-initialises through a `ContentProvider`, so no explicit init is needed in
  `VeniceApplication`. Do not add one.
- `settings.gradle.kts` uses `FAIL_ON_PROJECT_REPOS` with `google()` filtered by
  `includeGroupByRegex("com\\.google.*")`. Firebase artifacts are under `com.google.firebase`, so they
  resolve -- but confirm rather than assume, since the filter is easy to trip.
- **Consent is assumed granted** for this story; the consent gate is 9.3.1. Record the assumption in
  the change proposal rather than leaving it implicit. Firebase does expose `setConsent`, but wiring it
  without a way for the user to answer would be worse than not wiring it.
- Firebase's own reserved and automatically-collected event names must not be shadowed by custom events.
  Check the current reserved list during refinement -- it changes between SDK versions, so this is a
  Context7/docs lookup, not a from-memory decision.
- **Two things to verify against current docs when registering custom definitions:**
  1. How GA4 handles a `Boolean` parameter. `is_first_trip` may need sending as `"true"`/`"false"`
     strings, which registers it as a custom *dimension* rather than a metric. Either is workable, but it
     should be a deliberate choice recorded in the tracking plan, not whatever the `Bundle` happens to do.
  2. Whether GA4 permits an event parameter and a user property to share a name. The tracking plan
     deliberately keeps the two vocabularies disjoint so this never arises -- but confirm, because if the
     platform silently allows it, nothing will stop a future story reintroducing the collision.
- Events may take minutes to appear in standard GA4 reports; DebugView is near-real-time and is the
  right tool for the on-device verification criterion.
- `applicationIdSuffix = ".debug"` means the debug build has a different application id. The Firebase
  project needs **both** ids registered, or debug events will not be accepted. Easy to miss.
- `core/analytics` is not Kover-excluded -- the provider and its `Bundle` mapping need tests to clear the
  95% bound. Mock `FirebaseAnalytics`; do not require a device for unit tests.
- Conventions: `docs/guidelines/guidelines-analytics.md`.
