# 9.1.1 — Upgrade the Analytics Abstraction

**Epic:** Analytics
**Feature:** Analytics Foundation

## User Story

As a developer, I want the analytics abstraction to be clearly named, fully documented, and safe by
construction, so that adding a new analytics backend is a one-line change and the debug sink cannot
leak into a release build.

## Description

Venice already has a provider-agnostic analytics layer (`AnalyticsTracker` / `AnalyticsProvider` /
`AnalyticsEvent`, `CompositeAnalyticsTracker`, `LogAnalyticsProvider`, wired via `AnalyticsModule`).
It works, but it carries no documentation at all, its naming diverges from the convention used in
sibling projects, and its Logcat provider is active in **every** build type — including release, where
Logcat is readable over ADB by anyone with physical access to the device.

This story is a structural upgrade with **no change to which events are emitted or what they contain**.
That keeps it reviewable as a pure diff, separate from story 9.1.2 which changes the taxonomy itself.

The naming and documentation conventions are adopted from the `fakestore` project's analytics module,
which is the reference implementation for this pattern. What is deliberately *not* adopted from it:
the sealed-class taxonomy, the Hilt multibinding, and the per-provider filter all stay as Venice has
them — see `docs/guidelines/guidelines-analytics.md` for the reasoning.

### Move to `core/`

Analytics currently straddles `domain/analytics/` and `data/analytics/`. Neither is right: it carries
no business rules, and no use case or repository references it — the domain layer should not know it is
being observed. The giveaway is `StopTypeParam`, which would sit in `domain/analytics/` purely to
serialise `domain/model/StopType` for a third-party SDK.

Everything analytics moves to a new **`core/analytics/`** package, parallel to `data/`, `domain/`, and
`ui/`, per the `core/` charter added to `guidelines-android.md`. Contracts and implementations stay
together, because analytics is one cohesive concern — the composite client is not a repository and the
providers map no DTOs.

```
core/analytics/    AnalyticsClient.kt            (from domain/analytics/AnalyticsTracker.kt)
                   AnalyticsProvider.kt          (from domain/analytics/)
                   AnalyticsEvent.kt             (from domain/analytics/)
                   AnalyticsUserProperty.kt      new, this story
                   CompositeAnalyticsClient.kt   (from data/analytics/CompositeAnalyticsTracker.kt)
                   DebugAnalyticsProvider.kt     (from data/analytics/LogAnalyticsProvider.kt)
                   AnalyticsLogFormatter.kt      new, this story
```

`domain/analytics/` and `data/analytics/` are removed entirely. Test files move to the mirrored
`core/analytics/` path under `src/test`.

**Do the move in this story, not later.** Every one of these files is already being renamed here, so
the move is nearly free; deferring it means churning the same files twice. Use `git mv` so the history
follows.

`core/` is created with `analytics/` as its **only** occupant. `ui/util/WithMinimumDuration.kt` and the
OkHttpClient provision in `di/NetworkModule.kt` are fair future candidates, but moving them is outside
this epic — later stories can move things in as they touch them.

### Renames

| Current | Target |
|---------|--------|
| `AnalyticsTracker` | `AnalyticsClient` |
| `AnalyticsTracker.track(event)` | `AnalyticsClient.logEvent(event)` |
| `AnalyticsProvider.shouldTrack(event)` | `AnalyticsProvider.shouldLog(event)` |
| `AnalyticsProvider.track(event)` | `AnalyticsProvider.logEvent(event)` |
| `CompositeAnalyticsTracker` | `CompositeAnalyticsClient` |
| `LogAnalyticsProvider` | `DebugAnalyticsProvider` |
| ViewModel field `analyticsTracker` | `analyticsClient` |

`logEvent` matches the Firebase SDK's own method name, which reduces friction when the Firebase
provider lands in 9.2.1. `DebugAnalyticsProvider` states *when the provider may be used*, which is the
constraint that matters about it.

### User property API

The abstraction currently has no way to set a **user property** — a sticky attribute of the
installation that analytics backends attach to every subsequently logged event, used for segmenting
reports and defining audiences. Stories 9.1.2 and 9.2.1 both require user properties, so the API is
added here, where the abstraction lives.

```kotlin
interface AnalyticsTracking {
    fun logEvent(event: AnalyticsEvent)
    fun setUserProperty(property: AnalyticsUserProperty)
    fun trackException(throwable: Throwable, operation: AnalyticsOperation)
}

interface AnalyticsClient : AnalyticsTracking

interface AnalyticsProvider : AnalyticsTracking {
    fun shouldLog(event: AnalyticsEvent): Boolean
}
```

The shared `AnalyticsTracking` supertype declares the surface **once**. Declaring `logEvent` separately
on the client and the provider lets the two drift, and every operation added then has to be remembered
in two places — a cost already paid twice while designing this epic.

`AnalyticsClient` adds nothing of its own. It exists so call sites depend on a name that does not expose
`shouldLog`, which is a provider-internal concern.

`AnalyticsUserProperty` is a sealed class in `core/analytics`, mirroring how `AnalyticsEvent` bounds
event parameters — the same reasoning applies, and more strongly: a user property is attached to
*every* event, so a high-cardinality one becomes a de facto persistent identifier.

**This story adds the API but nothing calls it.** The two concrete properties
(`distance_unit`, `trip_count_band`) are defined and set by 9.1.2. `shouldLog` deliberately does not
gate user properties — filtering is an event-level concern, and a provider that wants to ignore a
property can no-op its own implementation.

### Exception channel

`trackException(throwable, operation)` is a **separate channel from events**, added here for the same
reason as the user property API: 9.2.2 needs it and this is where the abstraction lives.

It exists because crash reporting needs a **stack trace**, and the event taxonomy cannot carry one.
`OperationFailed` is bounded to enum values by design — that is what keeps free text and PII out of
product analytics — so there is nowhere on it to put a throwable. Without a separate channel the
Crashlytics provider would record non-fatals with no stack trace, which is most of its value gone.

The throwable **must never** become an event parameter. Product-analytics providers ignore
`trackException`; only crash-reporting providers act on it.

As with user properties, this story adds the API and nothing calls it — 9.1.2 wires the call sites.

### Debug-only registration

The Logcat provider must be registered in debug builds only. The gate is the **DI binding's source
set**, not a runtime flag:

```
app/src/main/java/…/core/analytics/DebugAnalyticsProvider.kt    class stays in main
app/src/debug/java/…/di/DebugAnalyticsModule.kt                 @Binds @IntoSet — debug only
```

The class stays in `main` so its unit test stays in the ordinary `src/test` source set and coverage
tooling needs no special case; R8 strips the unreferenced class from release builds.

Note that `app/src/debug/java/` does not exist yet — only `app/src/debug/res/`.

## Acceptance Criteria

1. **Client renamed** — `AnalyticsClient` replaces `AnalyticsTracker`, exposing `logEvent(event)`.
2. **Provider renamed** — `AnalyticsProvider` exposes `shouldLog(event)` and `logEvent(event)`.
3. **Implementations renamed** — `CompositeAnalyticsClient` and `DebugAnalyticsProvider`.
4. **All call sites updated** — both ViewModels use `analyticsClient.logEvent(...)`.
5. **Log formatting extracted** — the Logcat message is built by an `internal` function in its own
   file, not inline in the provider, so it is directly unit-testable.
6. **KDoc on every public type** covering: what it is for, how to register a provider, the
   thread-safety guarantee, the primitive-only parameter constraint, the prohibition on personal data,
   and — on `DebugAnalyticsProvider` — an explicit warning never to register it in release builds.
7. **Debug provider is bound in the debug source set only**, via a new
   `app/src/debug/java/…/di/DebugAnalyticsModule.kt`.
8. **Release variant compiles and runs with an empty provider set** — `AnalyticsModule` declares the
   multibound provider set explicitly so a variant with zero bindings still builds.
9. **A release build emits nothing** — no Logcat analytics output.
10. **A debug build behaves exactly as before** — same events, same parameters, same Logcat output
    apart from the changed log tag.
11. **Test double added** — a `@TestInstallIn` module replaces the provider set with a recording fake
    for instrumented tests. None exists today, so instrumented tests currently hit the real provider.
    The fake records user properties as well as events.
12. **No taxonomy change** — `AnalyticsEvent` and its members are untouched by this story.
13. **The tracking surface is declared once** in a shared `AnalyticsTracking` supertype;
    `AnalyticsClient` and `AnalyticsProvider` both extend it, and neither redeclares its operations.
14. **User property API exists** — `setUserProperty(property)` with `AnalyticsUserProperty` as a sealed
    class in `core/analytics`.
15. **Exception channel exists** — `trackException(throwable, operation)`, separate from events.
16. **`CompositeAnalyticsClient` fans user properties and exceptions out to every provider**, unfiltered
    — `shouldLog` gates events only.
17. **`DebugAnalyticsProvider` logs events, user properties, and exceptions distinguishably**, so
    on-device verification can tell the three apart in Logcat.
18. **A throwable never reaches an event parameter** — verified by inspection of the composite and the
    debug provider.
19. **The zero-provider case is a documented silent no-op** on `CompositeAnalyticsClient` — not an
    error, not a crash. This is the state a release build is in until 9.2.1 wires a backend.
20. **No call site uses the user property or exception APIs yet** — both are unused until 9.1.2, and
    that is intentional.
21. **All analytics code lives in `core/analytics/`** — `domain/analytics/` and `data/analytics/` no
    longer exist, and test files sit at the mirrored path.
22. **The move used `git mv`** so file history is preserved.
23. **No analytics type is referenced from `domain/` or `data/`** — verified by inspection; only
    `ui/viewmodel/` and `di/` may reference `core/analytics`.
24. **`core/` contains only `analytics/`** — nothing else was migrated as part of this story.

## Analytics

No new events, no changed events. This story changes only the delivery mechanism.

The one observable analytics behaviour change: **release builds stop emitting to Logcat**. Between
this story and 9.2.1 a release build has no provider at all and therefore emits nothing anywhere. That
is intended and temporary.

A user property API is introduced but left unused; the properties themselves are defined in the
tracking plan and set by 9.1.2.

## Technical Notes

- **`@Multibinds` is required, not optional.** With the debug binding moved out of `main`, a release
  build has zero `@IntoSet` contributions. Dagger will not synthesise an empty multibound set without
  an explicit declaration, so the release variant fails to compile. This is the single most likely
  thing to be missed.
- Verify **both** variants build: `./gradlew assembleDebug assembleRelease`. A debug-only build passing
  proves nothing about the change that matters most here.
- `di/` is excluded from Kover coverage (`*.di.*`), so the new debug module needs no test. The renamed
  `data/analytics` and `domain/analytics` classes are **not** excluded and must keep clearing the 95%
  bound — the existing tests need renaming alongside their subjects.
- Naming and documentation conventions: `docs/guidelines/guidelines-analytics.md`.
- Reference implementation for the naming and KDoc style: the `analytics` package of the `fakestore`
  project.
