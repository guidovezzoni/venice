# 9.2.1 — Send Events to Firebase Analytics

**Epic:** Analytics
**Feature:** Analytics Destinations

## User Story

As a product owner, I want events delivered to Firebase Analytics, so that I can actually see how the
app is used instead of relying on Logcat on my own device.

## Description

Events currently reach only a Logcat sink in debug builds. This story adds the first real destination.

Because the abstraction from 9.1.1 already exists, the integration itself is small: a new
`FirebaseAnalyticsProvider` and one `@Binds @IntoSet` line. The provider owns every Firebase-specific
concern — the `Bundle` mapping, event-name translation, and the platform's naming and size limits — so
no other layer becomes aware that Firebase exists. That containment is the whole point of the
abstraction and should not be eroded by letting Firebase types leak upward.

Firebase Analytics is free with unlimited event volume, and DebugView allows on-device verification of
real payloads, which matters because a taxonomy is only as good as what actually arrives.

The genuine costs are worth naming up front:

- The `google-services` Gradle plugin and a `google-services.json` file, which must never be committed
  and must be available to CI. `docs/improvements/github-ci-setup.md` currently records Firebase as
  absent from the project, so CI needs updating.
- Manifest merge adds `AD_ID` and `INTERNET`, which changes what must be declared on the Play Data
  Safety form.
- Analytics data is processed in US data centres.

Depends on 9.1.2 — shipping a real backend before the taxonomy is final would lock in names that can no
longer be changed without breaking accumulated data.

## Acceptance Criteria

1. **Dependencies added via the version catalog** — `firebase-bom`, `firebase-analytics`, and the
   `google-services` plugin. Versions live in `libs.versions.toml`; no hardcoded version strings.
2. **`google-services.json` is gitignored** and sourced the same way as `MAPS_API_KEY`, with a
   documented fallback when absent.
3. **A build without the config file fails with a clear message**, not a confusing plugin error.
4. **`FirebaseAnalyticsProvider` implements `AnalyticsProvider`** and maps `AnalyticsEvent` to a
   Firebase `Bundle`.
5. **Registered with a single `@Binds @IntoSet`** in `AnalyticsModule`, with no other wiring changes.
6. **No Firebase type appears outside `core/analytics` and `di`.**
7. **`screen_viewed` maps to Firebase's `SCREEN_VIEW`** event so it populates the built-in screen
   reports rather than sitting as an unrelated custom event.
8. **Firebase's automatic `screen_view` collection is disabled**, so the mapped event is the only source.
   Leaving both active double-counts screen views and corrupts the funnel that story 9.1.3 exists to make
   correct.
9. **Every other automatically-collected event is reviewed**, and any left enabled is a recorded decision
   with a tracking-plan entry. An automatic event that reaches the backend without appearing in the plan
   breaks the plan's "every event has an entry" rule and is invisible to code review.
10. **Platform limits are enforced in the provider**: event and parameter names ≤40 characters, string
    values ≤100 characters, ≤25 parameters per event, and no reserved `firebase_` / `google_` / `ga_`
    prefix. A violation must fail loudly in debug rather than being silently dropped.
11. **Both user properties are forwarded** to `FirebaseAnalytics.setUserProperty`.
12. **Both user properties are registered in the Firebase console** under *Analytics → Custom
    Definitions*, and the same is done for every custom event parameter in the tracking plan.
    Unregistered definitions are accepted silently by the SDK but never appear in reports or as
    audience criteria — which looks identical to a broken integration.
13. **Debug and release both build** — `./gradlew assembleDebug assembleRelease`.
14. **Release builds emit to Firebase** — the provider is bound in `main`, not the `debug` source set.
    This is the story that gives release builds a destination for the first time.
15. **DebugView verification**: with
    `adb shell setprop debug.firebase.analytics.app com.guidovezzoni.venice.debug`, exercise the full
    funnel and confirm every event arrives with the expected parameters, correctly typed, with no
    `(other)` bucketing and no missing parameters. Confirm both user properties are attached to
    events logged after they are set.
16. **Play Data Safety and the privacy policy are reviewed** against what the SDK actually collects.
17. **CI can build** without a committed config file.

## Analytics

No new events and no taxonomy change — this story only adds a destination for the events defined in
`docs/analytics/tracking-plan.md`.

Firebase-specific mappings owned by the provider:

| Domain event | Firebase event |
|--------------|----------------|
| `screen_viewed` | `SCREEN_VIEW` (reserved built-in) with `screen_name` |
| all others | logged verbatim as custom events |

## Technical Notes

- Firebase Analytics self-initialises through a `ContentProvider`, so no explicit init is needed in
  `VeniceApplication`. Do not add one.
- `settings.gradle.kts` uses `FAIL_ON_PROJECT_REPOS` with `google()` filtered by
  `includeGroupByRegex("com\\.google.*")`. Firebase artifacts are under `com.google.firebase`, so they
  resolve — but confirm rather than assume, since the filter is easy to trip.
- **Consent is assumed granted** for this story; the consent gate is 9.3.1. Record the assumption in
  the change proposal rather than leaving it implicit. Firebase does expose `setConsent`, but wiring it
  without a way for the user to answer would be worse than not wiring it.
- Firebase's own reserved and automatically-collected event names must not be shadowed by custom events.
  Check the current reserved list during refinement — it changes between SDK versions, so this is a
  Context7/docs lookup, not a from-memory decision.
- **Two things to verify against current docs when registering custom definitions:**
  1. How GA4 handles a `Boolean` parameter. `is_first_trip` may need sending as `"true"`/`"false"`
     strings, which registers it as a custom *dimension* rather than a metric. Either is workable, but it
     should be a deliberate choice recorded in the tracking plan, not whatever the `Bundle` happens to do.
  2. Whether GA4 permits an event parameter and a user property to share a name. The tracking plan
     deliberately keeps the two vocabularies disjoint so this never arises — but confirm, because if the
     platform silently allows it, nothing will stop a future story reintroducing the collision.
- Events may take minutes to appear in standard GA4 reports; DebugView is near-real-time and is the
  right tool for the on-device verification criterion.
- `applicationIdSuffix = ".debug"` means the debug build has a different application id. The Firebase
  project needs **both** ids registered, or debug events will not be accepted. Easy to miss.
- `core/analytics` is not Kover-excluded — the provider and its `Bundle` mapping need tests to clear the
  95% bound. Mock `FirebaseAnalytics`; do not require a device for unit tests.
- Conventions: `docs/guidelines/guidelines-analytics.md`.
