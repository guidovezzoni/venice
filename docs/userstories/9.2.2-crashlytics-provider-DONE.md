# 9.2.2 — Report Failures to Crashlytics

**Epic:** Analytics
**Feature:** Analytics Destinations
**Depends on:** 9.1.1 (analytics abstraction upgrade), 9.1.2 (analytics taxonomy), 9.2.1 (Firebase Analytics provider)

## User Story

As a developer, I want handled failures and crashes reported to Crashlytics, so that I learn about
problems users hit in the wild instead of only the ones I can reproduce.

## Description

The app currently has no crash reporting. Crashes are invisible, and handled failures — every
`operation_failed` event — are caught and shown to the user but never reported to a diagnostic
backend. Those are exactly the events worth recording as non-fatals, because they describe things
that went wrong without taking the process down.

This story adds a `CrashlyticsAnalyticsProvider` as a **separate provider** from the Firebase
Analytics one (`FirebaseAnalyticsProvider`). Keeping them independent means the product-analytics
backend can be swapped or dropped later without losing crash reporting, which is the more
operationally critical of the two.

### How the two channels map to Crashlytics

The analytics architecture (from 9.1.1) defines two channels that fire on every failure path:

| Channel | Carries | Purpose |
|---------|---------|---------|
| `trackException(throwable, operation)` | Real throwable with stack trace | Diagnostic: *where and why* it failed |
| `logEvent(OperationFailed(operation, errorType))` | Two bounded enum values | Product analytics: *how often* it fails |

The Crashlytics provider uses **both**, but for different purposes:

- **`trackException`** calls `FirebaseCrashlytics.recordException()` with the real throwable. This
  is where the stack trace comes from — the entire value of a non-fatal report. The `operation`
  value is set as a Crashlytics custom key before recording, so non-fatals can be filtered by
  operation in the console.
- **`logEvent` for `OperationFailed`** sets `error_type` as a Crashlytics custom key. This enriches
  the non-fatal grouping. All other events are ignored (no-op).
- **`setUserProperty`** forwards user properties as Crashlytics custom keys. Knowing whether a
  crashing user is on metric or imperial (for example) narrows a bug faster. The existing two
  user properties (`trip_count_band`, `distance_unit`) are forwarded.

A non-fatal must **never** be synthesised from an `OperationFailed` event. Doing so would produce a
throwable whose stack trace points at the analytics layer, not the failure site — technically a
report, practically useless.

### Crashlytics is a Firebase product

Crashlytics requires the `google-services` plugin and `google-services.json`, which already exist
from story 9.2.1. This story adds only the Crashlytics-specific dependencies and Gradle plugin. If
this story were ever done before 9.2.1, it would inherit the `google-services` setup work. The
providers are independent at the DI level, but share Firebase infrastructure.

### Consent and collection

Crashlytics collection is enabled by default and starts reporting at process start. Since consent is
assumed until story 9.3.1, that is accepted here. Note that `setCrashlyticsCollectionEnabled` is the
hook 9.3.1 will need, and it must be settable before the SDK initialises to be meaningful.

### Debug builds

Debug builds use `applicationIdSuffix = ".debug"`, which creates a separate Firebase app entry,
keeping development crash noise out of production data. Crashlytics collection remains enabled in
debug so developers can verify integration. The `.debug` suffix already provides separation.

## Acceptance Criteria

1. **Dependencies added via the version catalog** — `firebase-crashlytics` library and the
   `firebase-crashlytics-gradle` plugin are declared in `gradle/libs.versions.toml`. No hardcoded
   versions.
2. **Crash reporting works** — an uncaught exception in a release-configured build appears in the
   Crashlytics console.
3. **`CrashlyticsAnalyticsProvider` subscribes only to `OperationFailed`** in its `logEvent`,
   no-oping for every other event type.
4. **Non-fatals are recorded from `trackException`**, passing the real throwable to
   `FirebaseCrashlytics.recordException()` so the report carries the stack trace from the failure
   site, not the analytics layer.
5. **`operation` is set as a Crashlytics custom key** before `recordException` is called, so
   non-fatals can be grouped and filtered by operation in the console.
6. **`error_type` is set as a Crashlytics custom key** when an `OperationFailed` event is logged,
   enriching the non-fatal grouping context.
7. **User properties are forwarded as Crashlytics custom keys** via `setUserProperty`. Both
   `trip_count_band` and `distance_unit` are forwarded.
8. **A non-fatal is never synthesised from an `OperationFailed` event** — the throwable must come
   from the `trackException` channel.
9. **No personal data reaches Crashlytics custom keys** — they carry only bounded enum values from
   the tracking plan. No place names, no coordinates, no identifiers, no exception messages as
   custom keys.
10. **Exception messages are accepted in the throwable** (they are the diagnostic payload) **but
    never copied into a custom key or an event parameter** — the stack trace stays on the
    crash-reporting channel only.
11. **Registered with a single `@Binds @IntoSet`**, independent of the Firebase Analytics binding.
12. **Removing the Firebase Analytics provider leaves Crashlytics working** — verified by
    temporarily commenting out the analytics binding and confirming the build succeeds and crash
    reporting still functions.
13. **No Crashlytics type appears outside `core/analytics/` and `di/`.**
14. **Thread-safe** — `CrashlyticsAnalyticsProvider` is safe to call from any thread. Document this
    on the class.
15. **Debug and release both build** with the Crashlytics plugin applied.
16. **Native symbol upload** is either configured for release builds or its absence is explicitly
    recorded as an accepted limitation (Venice is a pure Kotlin/JVM app with no NDK code).
17. **On-device verification**: force a handled failure (airplane mode during route calculation) and
    confirm a non-fatal appears in the Crashlytics console with a stack trace pointing at the
    failure site, plus the expected custom keys (`operation`, `error_type`). Separately force a
    crash and confirm it is reported.

## Fields and Data

### Custom keys set on Crashlytics

These are Crashlytics-specific custom keys, not analytics event parameters. They are set via
`FirebaseCrashlytics.setCustomKey()` and appear in the Crashlytics console alongside crash and
non-fatal reports.

| Custom key | Type | Source | Set when |
|------------|------|--------|----------|
| `operation` | String | `AnalyticsOperation.value` | Before each `recordException` call |
| `error_type` | String | `AnalyticsErrorType.value` | On `logEvent(OperationFailed(...))` |
| `trip_count_band` | String | `CountBand.value` | On `setUserProperty(TripCountBand(...))` |
| `distance_unit` | String | `DistanceUnitParam.value` | On `setUserProperty(DistanceUnit(...))` |

All values are bounded enum strings from the tracking plan. No free text, no identifiers.

### No endpoints

This story has no network endpoints. Crashlytics SDK handles all data transmission internally.

## Original user story

### User Story

As a developer, I want handled failures and crashes reported to Crashlytics, so that I learn about
problems users hit in the wild instead of only the ones I can reproduce.

### Description

The app has no crash reporting at all: no Crashlytics, no
`Thread.setDefaultUncaughtExceptionHandler`, nothing. Crashes are currently invisible.

Separately, the app already knows about a class of problems it never reports — every `operation_failed`
event represents a failure that was caught and shown to the user. Those are exactly the events worth
recording as non-fatals, because they describe things that went wrong without taking the process down.

This story adds a Crashlytics provider as a **deliberately separate provider** from the Firebase
Analytics one. Keeping them independent means the product-analytics backend can be swapped or dropped
later without losing crash reporting, which is the more operationally critical of the two.

The provider no-ops its `logEvent` for events it does not care about, subscribing only to
`OperationFailed` and ignoring everything else, without the analytics provider or any call site knowing
it exists.

#### Non-fatals come from the exception channel, not the event

This is the part most likely to be got wrong. `FirebaseCrashlytics.recordException()` requires a real
`Throwable` — that is where the **stack trace** comes from, and the stack trace is essentially the whole
value of a non-fatal report. But `AnalyticsEvent.OperationFailed` deliberately carries only two bounded
enum values (`operation`, `error_type`) so that no free text or PII can reach product analytics. It has
nowhere to put a throwable.

So the non-fatal is driven by **`trackException(throwable, operation)`** — the separate channel added in
9.1.1 — not by the `operation_failed` event. Both fire on a failure path and they answer different
questions:

| Channel | This provider | Carries | Answers |
|---------|---------------|---------|---------|
| `trackException(throwable, operation)` | records a non-fatal | full throwable and stack trace | *where and why* it failed |
| `logEvent(OperationFailed(...))` | adds `error_type` as a custom key for grouping | bounded enums only | *how often* it failed |

Deriving the non-fatal from the event instead would mean synthesising a throwable at the provider,
producing a stack trace pointing at the analytics layer rather than the failure site — technically a
report, practically useless.

Depends on 9.1.1 for the exception channel, and on 9.1.2 for the `error_type` classification that makes
the non-fatals groupable rather than a wall of distinct raw messages.

### Technical Notes

- **Independence has a documented limit.** Crashlytics is itself a Firebase product and still requires
  the `google-services` plugin and `google-services.json`. If Firebase Analytics is dropped later, the
  SDK dependency and the `@IntoSet` binding go, but the Gradle plumbing stays. Worth stating plainly so
  the separation is not mistaken for more than it is.
- If 9.2.1 has already landed, the `google-services` plumbing exists and this story only adds the
  Crashlytics artefacts. If this story is ever done *first*, it inherits that setup work.
- Crashlytics collection is enabled by default and starts reporting at process start. Since consent is
  assumed until 9.3.1, that is accepted here — but note that `setCrashlyticsCollectionEnabled` is the
  hook 9.3.1 will need, and it must be settable *before* the SDK initialises to be meaningful.
- Debug builds report crashes too, which pollutes the console with development noise. Decide during
  refinement whether to disable collection in debug; the `applicationIdSuffix = ".debug"` at least keeps
  them separable.
- Non-fatals are throttled by the SDK. A high-frequency failure will not produce one report per
  occurrence, so counts in Crashlytics are not a substitute for the `operation_failed` counts in
  Analytics. The two answer different questions.
- `core/analytics` is not Kover-excluded — the provider needs tests clearing the 95% bound, with
  `FirebaseCrashlytics` mocked.
