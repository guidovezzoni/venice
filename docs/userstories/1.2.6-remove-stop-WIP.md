# 1.2.6 — Remove a Stop

**Epic:** Trip Management
**Feature:** Stop Management

## User Story

As a user, I want to remove a stop from my roadtrip so that I can simplify my journey or correct a mistake.

## Description

The user can delete any stop (starting point, intermediate, or destination). A confirmation dialog is shown before deletion to prevent accidental removal. After deletion, remaining stop orders are recalculated to be contiguous. Special promotion rules apply when the starting point or destination is removed.

## Acceptance Criteria

1. The user can remove any intermediate stop via a delete button on the stop card.
2. The user can remove the starting point or the destination via a delete button on the stop card.
3. A confirmation dialog is shown before any deletion, displaying the stop's place name.
4. After removing an intermediate stop, remaining stop orders are recalculated to be contiguous (no gaps).
5. If the starting point (order 0) is removed and other stops exist, the next stop (order 1) is promoted to order 0 (becomes the new starting point).
6. If the destination (highest order) is removed and other stops exist, the previous stop becomes the new destination.
7. A trip can have zero stops (removing the last stop leaves an empty trip).
8. The delete operation is performed within a database transaction to ensure atomicity.
9. On failure, a snackbar error is shown and no changes are persisted.

## Technical Detail

### Layer: Data — `StopDao`

Add a new method to `StopDao`:

```kotlin
@Query("DELETE FROM stops WHERE id = :stopId")
suspend fun deleteById(stopId: String)
```

Add a new transactional method:

```kotlin
@Transaction
suspend fun deleteAndReorder(tripId: String, stopId: String)
```

This method:
1. Queries the stop to delete via `getStopById(stopId)` to obtain its `order`.
2. Deletes the stop via `deleteById(stopId)`.
3. Decrements the `order` of all stops in the same trip where `order > deletedOrder`.

This requires a new DAO query:

```kotlin
@Query("UPDATE stops SET `order` = `order` - 1 WHERE tripId = :tripId AND `order` > :fromOrder")
suspend fun decrementOrderAbove(tripId: String, fromOrder: Int)
```

### Layer: Domain — `StopRepository` interface

Add:

```kotlin
suspend fun deleteStop(tripId: String, stopId: String): Result<Unit>
```

### Layer: Data — `StopRepositoryImpl`

Implement `deleteStop`:
1. Delegate to `StopDao.deleteAndReorder(tripId, stopId)`.
2. Wrap in `runCatching` for the `Result` pattern.

### Layer: Domain — `RemoveStopUseCase`

New use case in `domain/usecase/RemoveStopUseCase.kt`:

```kotlin
class RemoveStopUseCase @Inject constructor(
    private val stopRepository: StopRepository,
) {
    suspend operator fun invoke(tripId: String, stopId: String): Result<Unit> {
        return stopRepository.deleteStop(tripId, stopId)
```

### Security, GDPR, and performance

- **Security**: No new external input; stop IDs are internal UUIDs. No injection risk.
- **GDPR**: Stop data (place names, coordinates) is local-only. Deletion removes data permanently — no soft-delete or audit trail needed.
- **Performance**: The `deleteAndReorder` transaction performs one DELETE and one UPDATE. Both operate on indexed columns (`id`, `tripId`, `order`). With a max of 25 stops per trip, performance is negligible.

## Original User Story

### User Story

As a user, I want to remove a stop from my roadtrip so that I can simplify my journey or correct a mistake.

### Description

The user can delete an intermediate stop. The remaining stops reorder to close the gap. Removing the starting point or destination requires special handling — the adjacent stop is promoted.

### Acceptance Criteria

- The user can remove any intermediate stop.
- Remaining stop orders are recalculated to be contiguous.
- If the starting point is removed, the next stop becomes the new starting point.
- If the destination is removed, the previous stop becomes the new destination.
- A trip cannot have fewer than zero stops (removing the last stop leaves an empty trip).
- Previously calculated legs involving the removed stop are invalidated.

### Technical Notes

- Provide a confirmation dialog before deletion to prevent accidental removal.
- Invalidation affects the legs on either side of the removed stop; they merge into a single new uncalculated leg.
