# 1.2.2 — Set a Destination

**Epic:** Trip Management
**Feature:** Stop Management
**Status:** WIP
**Depends on:** 1.2.1 (Set Starting Point — reuses the `Stop` data model, `StopDao`, and `StopRepository`)

## User Story

As a user, I want to set a destination for my roadtrip so that the route calculation knows where I'm heading.

## Functional Description

When the user opens a trip's detail screen, they see a dedicated **Destination** section below the Starting Point section. If no destination has been set, a placeholder with a *Set destination* call-to-action is shown. Tapping it triggers place search (Epic 2); once a place is selected its name and coordinates are saved as a stop with the highest `order` value.

The destination is visually distinct from the starting point and future intermediate stops (dedicated icon — `Place` — and label "Destination"). The user can tap the destination at any time to change it, which updates the existing stop in place rather than adding a new one.

> **Scope note:** until user story 2.1.1 (Place Search) is implemented, a simple stub dialog with *Place name*, *Latitude*, and *Longitude* text fields is used — identical in structure to the starting point stub dialog.

> **Design note — identifying the destination:** In this story, the destination is identified as the stop with the highest `order` where `order > 0`. This convention works while only starting point and destination exist. Story 1.2.3 (add intermediate stops) will need to introduce a `StopType` enum or similar mechanism to distinguish the destination from the last intermediate stop; that migration is deferred to 1.2.3.

## Acceptance Criteria

1. The Destination section is visible in `TripDetailScreen`, below the Starting Point section.
2. When no destination exists a placeholder with a *Set destination* button is shown.
3. Tapping *Set destination* (or the existing destination to change it) opens the stub dialog (name + lat + lng fields).
4. The destination is saved with `order = 1` (when only a starting point exists), `placeName`, `latitude`, `longitude`, and `status = PENDING`.
5. If a destination already exists, confirming a new selection replaces it (upsert on the max-order stop).
6. The destination is visually distinguished from the starting point (e.g. `Place` icon, label "Destination").
7. The destination persists across app restarts (stored in Room).
8. Input is validated: place name must be non-blank; latitude in `[-90, 90]`; longitude in `[-180, 180]`. Inline errors shown on invalid input.

## Data Model

No new data model files are required. The destination reuses the existing `Stop` domain model and `StopEntity` from story 1.2.1.

### Destination identification convention

- Starting point: `order = 0`
- Destination: max `order` where `order > 0` (currently always `order = 1` since intermediate stops do not exist yet)

No database migration is needed — the existing `stops` table supports this without schema changes.

## Repository Changes

### `StopRepository` interface — add:

```kotlin
    tripId: String,
    placeName: String,

    longitude: Double,
): Result<Stop>
```

### `StopRepositoryImpl` — implement:

```kotlin
private const val DESTINATION_DEFAULT_ORDER = 1

override suspend fun upsertDestination(
    tripId: String,
    placeName: String,
    latitude: Double,
    longitude: Double,
): Result<Stop> = runCatching {
    val existing = stopDao.getDestination(tripId)
    val entity = if (existing != null) {
        existing.copy(
            placeName = placeName,
            latitude = latitude,
            longitude = longitude,
        ).also { stopDao.update(it) }
    } else {
        StopEntity(
            id = UUID.randomUUID().toString(),
            tripId = tripId,
            placeName = placeName,
            latitude = latitude,
            longitude = longitude,
            order = DESTINATION_DEFAULT_ORDER,
            status = StopStatus.PENDING.name,
        ).also { stopDao.insert(it) }
    }
    entity.toDomain()
}
```

## Use Case

```kotlin
class SetDestinationUseCase @Inject constructor(
    private val stopRepository: StopRepository,
) {
    suspend operator fun invoke(
        tripId: String,
        placeName: String,
        latitude: Double,
        longitude: Double,
    ): Result<Stop> =
        stopRepository.upsertDestination(tripId, placeName.trim(), latitude, longitude)
}
```

## Non-Functional Considerations

### Security

- No sensitive credentials or tokens are involved.
- Input validation guards against malformed coordinates before persisting (`latitude ∈ [-90, 90]`, `longitude ∈ [-180, 180]`).
- All data is stored locally (SQLite); no network calls in this story.

### Performance

- Reuses the existing `observeStopsForTrip` Flow — no additional database queries for observing the destination.
- The destination is extracted in-memory from the same stops list already observed for the starting point.
- The upsert performs at most 2 DAO operations (`getDestination` + `insert`/`update`), both on Room's default IO executor.

### GDPR / Privacy

- Latitude and longitude constitute location data and are PII under GDPR Art. 4(1).
- In this story, data is stored **on-device only** (Room/SQLite) — no data leaves the device.
- If a future story adds cloud sync or backup, coordinates must be flagged as sensitive and handled accordingly (encryption at rest, explicit user consent).

### Accessibility

- The *Set destination* button must have a `contentDescription` for screen readers.
- The stub dialog's text fields must have proper labels (`OutlinedTextField` with `label` parameter) rather than hint-only descriptions.

## Original User Story

### 1.2.2 — Set a Destination

**Epic:** Trip Management
**Feature:** Stop Management

#### User Story

As a user, I want to set a destination for my roadtrip so that the route calculation knows where I'm heading.

#### Description

The user designates a location as the final stop of the trip. The destination is selected via place search and stored with its name and coordinates. A trip must have both a starting point and a destination before a route can be calculated.

#### Acceptance Criteria

- The user can set a destination via place search.
- The destination is stored as the last stop (highest order) with name, latitude, and longitude.
- The destination is visually distinguished from intermediate stops in the UI.
- The destination can be changed after initial selection.
- Adding intermediate stops does not displace the destination — it always remains last.

#### Technical Notes

- Uses the same `Stop` data model as 1.2.1. The destination is the stop with the highest `order` value.
- When intermediate stops are added (1.2.3) or reordered (1.2.4), the destination's order must be recalculated to remain last.
