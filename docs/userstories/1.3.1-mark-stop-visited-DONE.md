# 1.3.1 — Mark a Stop as Visited/Departed

**Epic:** Trip Management
**Feature:** Stop Progress

## User Story

As a user, I want to mark a stop as visited/departed so that I can track my progress along the roadtrip.

## Description

While on the trip, the user can manually mark a stop as completed/departed. This updates the stop's status and shifts the "current position" in the trip to the next stop. In Level 1, this is a manual action; in Level 2, it could be augmented with GPS proximity detection.

The UI should visually distinguish three logical states for each stop:
- **Departed** — the user has already left this stop
- **Current** — the next stop to be departed (derived: first non-departed stop by order)
- **Upcoming** — all stops after the current one

## Acceptance Criteria

- Each stop has a status: `upcoming`, `current`, or `departed`.
- The user can mark the current stop as departed.
- Marking a stop as departed automatically sets the next stop as `current`.
- The starting point can be marked as departed (the trip has begun).
- The action is reversible — the user can undo marking a stop as departed.

## Technical Specification

### Data Model

The `StopStatus` enum already exists with values `PENDING` and `VISITED`. No schema migration is needed:

| Persisted Status | UI Label | Meaning |
|---|---|---|
| `PENDING` | Upcoming / Current | Stop not yet departed |
| `VISITED` | Departed | User has left this stop |

The `CURRENT` concept is **derived, not stored**: the current stop is the first `PENDING` stop (lowest `order`) in the trip. This avoids data-consistency issues (e.g. two stops both marked `CURRENT`) and keeps the existing DB schema unchanged.

### Security Considerations

- **No concerns.** All data is local; no user-facing input beyond tapping a button. No PII is involved in the status field.

### Performance Considerations

- **Minimal impact.** Updating a single row's `status` column is O(1) in Room. The `observeByTripId` Flow already emits on any stop change, so the UI will reactively update without additional queries.
- The "current stop" derivation is computed from an already-loaded in-memory list (max 27 stops: 1 start + 25 intermediates + 1 destination), negligible cost.

### GDPR / Sensitive Information

- **No concerns.** Stop status (`PENDING`/`VISITED`) contains no personal or sensitive data.

### Non-Functional Requirements

- **Offline-first:** The feature works entirely offline, consistent with the app's design.
- **Data integrity:** Using Room's existing `@Update` mechanism ensures atomicity. No cross-table consistency constraints needed — status is a single-column update.
- **Future extensibility:** The "derived current" pattern cleanly supports the Level 2 GPS upgrade path described in the original story. A future `PositionProvider` interface can determine "current" from GPS proximity instead of manual marking, without changing the persisted model.

### Technical Notes

- **Data model:** Add `status` enum to `Stop`: `UPCOMING | CURRENT | DEPARTED`.
- The concept of "current position = last departed stop" is the foundation for Level 2 GPS upgrades. In Level 1, `currentPosition = lastDepartedStop.latLng`. In Level 2, `currentPosition = gps.latLng`. Abstract this behind a position provider interface to make the transition clean.
