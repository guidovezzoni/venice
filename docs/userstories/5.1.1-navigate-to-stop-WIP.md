# 5.1.1 — Open Google Maps Navigation to a Stop

**Epic:** Navigation Handoff
**Feature:** Launch Navigation
**Status:** WIP

## User Story

As a user, I want to tap a "Navigate" action on a stop and open Google Maps (or any available maps app) in navigation mode directed to that stop, so that I get turn-by-turn directions without the app having to build its own navigation.

## Description

Each stop displayed on the trip detail screen gains a "Navigate" button. Tapping it fires an Android implicit Intent that launches a navigation app (preferring Google Maps) with the stop's stored coordinates as the destination. The app itself performs no navigation, routing, or tracking -- it simply hands off to the external app.

The action is available on all stops that have valid coordinates and are not yet departed (i.e. stops whose `StopStatus` is `PENDING`). Departed stops already have no meaningful navigation value since the user has already left them, so the navigate action is hidden for those. The starting point, when it is the only departed stop, also does not show the action.

If no app capable of handling the navigation intent is installed on the device, the user is shown a brief error message (snackbar or toast) explaining that no navigation app was found.

## Acceptance Criteria

1. **Navigate action visible** -- Every stop card with `StopStatus.PENDING` displays a "Navigate" button/icon button.
2. **Navigate action hidden** -- Stops with `StopStatus.VISITED` (departed) do not display the navigate action.
3. **Google Maps intent** -- Tapping "Navigate" launches a `google.navigation:q={latitude},{longitude}` Intent that opens Google Maps in turn-by-turn navigation mode.
4. **Fallback intent** -- If the Google Maps intent cannot be resolved (Google Maps not installed), the app falls back to a `geo:{latitude},{longitude}?q={latitude},{longitude}({placeName})` URI intent so other map applications can handle it.
5. **No app available** -- If neither intent can be resolved by any installed application, the user sees a user-friendly error message (e.g. "No navigation app found").
6. **Coordinates used directly** -- The intent uses the stop's persisted `latitude` and `longitude` values, not a text-based search query.
7. **Label included in fallback** -- The `geo:` fallback URI includes the stop's `placeName` as a label so the user can confirm the destination in the receiving app.
8. **No permissions required** -- Launching an implicit intent to another app does not require any runtime permission.
9. **Disabled during loading** -- The navigate button is disabled (like other action buttons) when the screen is in a loading state (`isLoading = true`).
10. **Accessibility** -- The navigate button has an appropriate content description (e.g. "Navigate to {placeName}").

## Fields and MVI Artefacts

### UiIntent (new entry)

| Intent | Data | Purpose |
|--------|------|---------|
| `OnNavigateToStopClicked` | `stopId: String` | User taps Navigate on a stop card |

### UiEffect (new entry)

| Effect | Data | Purpose |
|--------|------|---------|
| `LaunchNavigation` | `latitude: Double, longitude: Double, placeName: String` | Signals the composable/activity to fire the navigation intent |
| `ShowNavigationError` | `message: String` | Shown when no navigation app can handle the intent |

### UiState

No new UiState fields are required. The navigate button visibility is derived from the stop's existing `StopStatus` field and the existing `isLoading` flag. The composable receives its stop data from the already-existing `Stop` model in the state.

## Intent URIs

| Priority | URI scheme | Example | Behaviour |
|----------|-----------|---------|-----------|
| Primary | `google.navigation:q={lat},{lng}` | `google.navigation:q=43.7696,11.2558` | Opens Google Maps in navigation mode |
| Fallback | `geo:{lat},{lng}?q={lat},{lng}({label})` | `geo:43.7696,11.2558?q=43.7696,11.2558(Florence, Italy)` | Opens any registered map app with the labelled destination |

Notes:
- The `placeName` must be URI-encoded before embedding in the `geo:` URI.
- No API key, SDK dependency, or network call is needed -- this is purely an intent launch.

## Security Considerations

| Concern | Risk | Mitigation |
|---------|------|------------|
| Intent injection | An attacker could theoretically craft a stop with malicious coordinates or place name to produce an unintended URI | Coordinates are `Double` values (cannot contain arbitrary strings); `placeName` is URI-encoded before embedding. The intent targets a well-defined URI scheme handled by trusted system apps. |
| Data leakage to third-party app | The navigation intent exposes the stop's coordinates and name to the receiving app | This is the explicit, expected behaviour. The user is actively choosing to navigate. No additional personal data (trip name, other stops, user account info) is sent. |
| Denial of service | Rapid repeated taps could launch multiple navigation intents | Standard Android behaviour; the external app will handle or ignore duplicate launches. No rate-limiting needed. |

**Verdict:** Low risk. No mitigation beyond URI encoding is required.

## Performance Considerations

| Concern | Risk | Mitigation |
|---------|------|------------|
| Intent resolution latency | Checking if an app can handle the intent could theoretically be slow | `PackageManager.resolveActivity()` is a synchronous system call that executes in microseconds. No async wrapper needed. |
| No network call | This feature does not make any API call or database query | N/A -- performance impact is negligible |

**Verdict:** No performance concerns. The feature is a single-line intent launch with no I/O.

## GDPR and Sensitive Information

| Concern | Risk | Mitigation |
|---------|------|------------|
| Location data shared with third-party | The stop's coordinates are passed to Google Maps or another navigation app | This is user-initiated (the user explicitly taps "Navigate"). The data shared is the destination coordinate, not the user's current location. The coordinate was already entered/selected by the user. No consent prompt is needed beyond the user's tap action. |
| No tracking or analytics of navigation | The app does not log which stops the user navigates to externally | If analytics are added in the future, this should be considered. Currently no concern. |
| No PII in the intent | Only coordinates and a user-provided place name are shared | No email, phone, account ID, or device identifiers are included in the intent. |

**Verdict:** No GDPR concern. The shared data is minimal, user-initiated, and does not constitute personal data processing beyond what the user explicitly requested.

## Other Non-Functional Requirements

| Concern | Detail |
