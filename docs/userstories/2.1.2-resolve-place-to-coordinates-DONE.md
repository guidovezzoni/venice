# 2.1.2 — Resolve Place Names to Coordinates

**Epic:** Place Search
**Feature:** Geocoding

## User Story

As a user, I want the app to resolve place names to coordinates so that routes can be calculated between my stops.

## Description

When a place is selected from search results, the app obtains its geographic coordinates (latitude, longitude). These coordinates are stored with the stop and used as input to the Google Directions API for route calculation.

## Current Implementation Status

The core coordinate resolution flow was already implemented as part of story 2.1.1 (Search Place by Name):

- **Place Details API call**: `PlaceSearchRepositoryImpl.getPlaceDetails()` fetches `DISPLAY_NAME` and `LOCATION` fields for a selected place.
- **Domain model**: `PlaceDetail` holds `name`, `latitude`, `longitude` (all `Double`).
- **ViewModel wiring**: `TripDetailUiIntent.OnSuggestionSelected` triggers `GetPlaceDetailUseCase`, populates `selectedPlaceDetail` in `TripDetailUiState`.
- **Dialog auto-fill**: `SetStopDialog` observes `selectedPlaceDetail` via `LaunchedEffect` and populates coordinates into text fields as read-only.
- **Storage**: coordinates are passed through `SetStopUseCase` / `EditStopUseCase` → `StopRepository` → Room database as `REAL NOT NULL`.

## Remaining Gaps

This story focuses on the UX gaps in the existing flow:

### Gap 1: No loading indicator during Place Details fetch

When the user taps an autocomplete suggestion, the `GetPlaceDetailUseCase` API call fires but there is no visual feedback in the dialog. On slow connections this could appear unresponsive.

**Fix**: Add a `isResolvingPlace: Boolean` field to `TripDetailUiState`. Set it `true` before calling `getPlaceDetailUseCase`, `false` on success or failure. Show a progress indicator in `SetStopDialog` when resolving. Disable the confirm button while resolving.

**Files to modify**:
- `app/src/main/java/com/guidovezzoni/venice/ui/state/TripDetailUiState.kt` — add `isResolvingPlace` field
- `app/src/main/java/com/guidovezzoni/venice/ui/viewmodel/TripDetailViewModel.kt` — toggle `isResolvingPlace` around `getPlaceDetailUseCase` call
- `app/src/main/java/com/guidovezzoni/venice/ui/screens/tripdetail/SetStopDialog.kt` — accept and display `isResolvingPlace` indicator, disable confirm
- `app/src/main/java/com/guidovezzoni/venice/ui/screens/tripdetail/TripDetailScreen.kt` — pass `isResolvingPlace` from state to dialog

### Gap 2: Place Details error shown as Snackbar behind the dialog

On failure, `TripDetailUiEffect.ShowError` emits a Snackbar at the screen level. Since the dialog is still open, the Snackbar may be hidden behind it. The user should see the error inline in the dialog.

**Fix**: Introduce a `placeDetailError: String?` field in `TripDetailUiState`. On `getPlaceDetailUseCase` failure, set this field instead of emitting `ShowError`. Display the error inline in the dialog (similar to how `searchError` is shown for autocomplete errors). Clear the error when the user taps another suggestion or types a new query.

**Files to modify**:
- `app/src/main/java/com/guidovezzoni/venice/ui/state/TripDetailUiState.kt` — add `placeDetailError` field
- `app/src/main/java/com/guidovezzoni/venice/ui/viewmodel/TripDetailViewModel.kt` — set `placeDetailError` on failure instead of emitting effect, clear on new search/selection
- `app/src/main/java/com/guidovezzoni/venice/ui/screens/tripdetail/SetStopDialog.kt` — accept and display `placeDetailError` inline
- `app/src/main/java/com/guidovezzoni/venice/ui/screens/tripdetail/TripDetailScreen.kt` — pass `placeDetailError` from state to dialog
- `app/src/main/res/values/strings.xml` — add error message string

### Gap 3: Retry after failure

After a Place Details failure, the autocomplete suggestions remain visible (the list is not cleared on failure), so the user can tap the same suggestion again. This is adequate retry behaviour — no additional UX is needed. However, a brief inline error message (Gap 2) must inform the user that resolution failed and they can try again.

## Acceptance Criteria

- AC1: Every stop has a valid `Double` latitude and longitude after place selection — **already satisfied**.
- AC2: Coordinates are obtained automatically as part of the place selection flow (no manual input from the user) — **already satisfied**.
- AC3: While the app is resolving a place to coordinates, a loading indicator is shown in the dialog and the confirm button is disabled.
- AC4: If coordinate resolution fails, an inline error message is shown inside the dialog (not as a Snackbar behind it).
- AC5: After a resolution failure, the user can tap the same or a different suggestion to retry.

## Original User Story

### User Story

As a user, I want the app to resolve place names to coordinates so that routes can be calculated between my stops.

### Description

When a place is selected from search results, the app obtains its geographic coordinates (latitude, longitude). These coordinates are stored with the stop and used as input to the Google Directions API for route calculation.

### Acceptance Criteria

- Every stop has a valid latitude and longitude after place selection.
- Coordinates are obtained automatically as part of the place selection flow — no manual input from the user.
- If coordinate resolution fails (network error, ambiguous result), the user is informed and can retry.

### Technical Notes

- **API:** When using Places Autocomplete (2.1.1), the Place Details endpoint returns coordinates for the selected place. This is a single follow-up call after the user picks a suggestion.
- **Flow:** User types → Autocomplete returns predictions → User picks one → Place Details returns lat/lng → stored on Stop.
- Coordinates must be stored as `Double` (not `Float`) to preserve precision for the Directions API.
