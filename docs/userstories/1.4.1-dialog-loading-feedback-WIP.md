# 1.4.1 — Loading Feedback for DB Operations

**Epic:** Trip Management
**Feature:** UI Feedback
**Status:** WIP

## User Story

As a user, I want to see a loading spinner and have action buttons disabled while any database operation is in progress, so that I know my action is being processed and I don't accidentally trigger duplicate or conflicting actions.

## Description

Both `TripDetailViewModel` and `TripListViewModel` already declare `isLoading` in their UI state, but usage is incomplete. This story wires `isLoading` through consistently across all async operations, disables buttons during loading, and adds a visible spinner.

### 8. Minimum Loading Duration

A reusable `withMinimumDuration` suspend utility SHALL ensure the loading state is displayed for at least 500 ms. It runs the async operation and a `delay(500)` in parallel, returning only when both complete. If the operation takes longer than 500 ms, the loading state naturally extends to match.

- Create `withMinimumDuration` in `ui/util/WithMinimumDuration.kt` with `minimumMillis` parameter defaulting to `MINIMUM_LOADING_DURATION_MILLIS` (500L), defined as a file-level private constant in the utility file
- Both `TripDetailViewModel` and `TripListViewModel` wrap all async use case calls with `withMinimumDuration { ... }` (no need to pass the duration explicitly)
- Unit test for `withMinimumDuration` using `StandardTestDispatcher` to verify timing behaviour

## No New Endpoints

This is a purely UI/ViewModel story. No network calls or new endpoints are involved. All operations are local Room database calls.

## No New String Resources

Buttons keep their existing text — they are just disabled during loading. The `CircularProgressIndicator` is a visual-only element with no text. No `strings.xml` changes needed.

## Security Considerations

- **Double-submission prevention**: Disabling buttons during async operations prevents duplicate database writes (e.g. creating the same trip twice, removing a stop twice). This is the primary security benefit of this story.
- **No new attack surface**: No new inputs, endpoints, or data flows are introduced.

## Performance Considerations

- **Negligible overhead**: Setting a boolean flag before/after an async call adds no measurable cost.
- **Spinner rendering**: `CircularProgressIndicator` is a lightweight Material 3 composable — no performance concern.
- **No blocking**: All operations remain on background dispatchers via coroutines; the UI thread only updates the state flag.

## GDPR / Sensitive Information

- No personal data is collected, stored, or transmitted by this change.
- No new permissions are required.

## Other Non-Functional Requirements

- **Accessibility**: `CircularProgressIndicator` has built-in semantics for screen readers. Disabled buttons are automatically announced as disabled by TalkBack.
- **Consistency**: All async operations will follow the same loading pattern, reducing cognitive overhead for future development.

## Original User Story

### 1.4.1 — Loading Feedback for DB Operations

**Epic:** Trip Management
**Feature:** UI Feedback

### User Story

As a user, I want to see a loading spinner and have action buttons disabled while any database operation is in progress, so that I know my action is being processed and I don't accidentally trigger duplicate or conflicting actions.

### Description

Both `TripDetailViewModel` and `TripListViewModel` already have `isLoading` in their UI state, but its usage is incomplete:

- **Missing coverage**: Not all DB operations set `isLoading` (e.g. `editStop()` in `TripDetailViewModel`).
- **No UI wiring**: Neither screen passes `isLoading` to dialog composables, and no spinner is shown anywhere during operations.
- **Buttons remain enabled**: Confirm buttons in dialogs and action buttons on screens stay active during async operations, allowing double-submission or conflicting actions.

This story ensures that **every DB operation** — creating, saving, editing, removing, reordering, marking departed — follows the same pattern:

1. Set `isLoading = true` before the async call.
2. Show a loading spinner while `isLoading` is `true`.
3. Disable contextually relevant buttons while `isLoading` is `true`.
4. Set `isLoading = false` on completion (success or failure).
5. Ensure the loading state is visible for a **minimum of 500 ms**, even if the operation completes faster, so the user perceives the feedback. This prepares the UX for future networking where operations will naturally take longer.

### Affected operations

- **TripListScreen**: creating a trip (confirm button in `CreateTripDialog`).
- **TripDetailScreen**: setting starting point, setting destination, adding a stop, editing a stop (confirm button in `SetStopDialog`), removing a stop, reordering stops, marking a stop as departed.

### Acceptance Criteria

1. Every async DB operation in `TripDetailViewModel` and `TripListViewModel` sets `isLoading = true` before the call and `false` on completion (success or failure).
2. The loading state is visible for a minimum of 500 ms, even if the operation completes faster.
3. The confirm button in `SetStopDialog` is disabled while `isLoading` is `true`.
4. The confirm button in `CreateTripDialog` is disabled while `isLoading` is `true`.
5. Action buttons on `TripDetailScreen` (remove stop, reorder, mark departed) are disabled while `isLoading` is `true`.
6. A loading spinner is displayed on the screen while `isLoading` is `true`.
7. All existing unit tests continue to pass.
8. Previews exist showing the loading state (spinner visible, buttons disabled) for both dialog composables and both screens.

### Technical Notes

- The OpenSpec main specs need updating: `destination-ui` (SetStopDialog), `trip-detail` (ViewModel loading behaviour, screen wiring), `trip-list` (TripListUiState `isLoading`, screen wiring), and `trip-creation` (CreateTripDialog).
- The `edit-intermediate-stop` delta spec should be updated to include `isLoading` in the `OnEditStopConfirmed` flow.
- No new string resources needed — buttons keep their existing text, they are just disabled.
- `isLoading` is already declared in both `TripDetailUiState` and `TripListUiState` — the work is wiring it through consistently and adding the spinner.
