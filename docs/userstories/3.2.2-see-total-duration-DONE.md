# 3.2.2 — See Total Estimated Duration of the Roadtrip

**Epic:** 3 — Route Calculation
**Feature:** 3.2 — Trip Totals
**Status:** Refined (WIP)

---

## 1. Functionality Overview

On the **Trip Detail** screen the user can already calculate a route, see the duration
of each individual leg (story 3.1.3), and see the total distance for the whole trip
(story 3.2.1). This story adds a single **total estimated driving duration** for the
whole trip: the sum of every calculated leg duration, presented once, clearly labelled as
driving time only.

The total gives the user an immediate sense of how long the journey will take
("this trip is about 5h 30min of driving") without adding up the legs themselves.

### Behaviour at the "what" level

- The trip overview shows a **total estimated driving duration** for the trip.
- The total equals the **sum of all individual calculated leg durations**.
- The total is clearly **labelled as driving time only** (it does not include time spent
  at stops). The label must make this distinction unambiguous.
- The total uses the **same duration formatting rules** already applied to individual legs
  (sub-hour: "45 min"; multi-hour: "2h 15min" -- see `DurationFormatter`), so the format
  is consistent across the screen.
- The total **updates automatically** whenever the route is (re)calculated, without any
  extra user action.
- When the trip's route is **not currently available** (no route has been calculated yet,
  or a stop change has invalidated the previously calculated route), the total is shown as
  **unavailable** rather than showing a misleading or zero value.
- The total duration is displayed **alongside the existing total distance** in the
  `TripTotalSummary` composable, so both trip totals appear together in a consistent
  summary area.

### Route-availability model (grounded in current code)

The existing invalidation is **all-or-nothing**: any stop mutation (set, edit, move,
remove) deletes **all** legs for the trip (`InvalidateRouteUseCase` ->
`deleteLegsForTrip`). Consequently, in the current implementation the stored legs are
either:

- **Complete** -- one leg exists for every consecutive pair of placed stops
  (`legs.size == placedStopCount - 1`, with `placedStopCount >= 2`), or
- **Absent** -- no legs exist (route never calculated, or invalidated by a stop change).

A genuinely *partial* set of legs does not occur today. The acceptance criteria therefore
treat "route not complete" as a single **unavailable** state. The original story's
"partial with a warning" wording is preserved below but is **not required** given the
current all-or-nothing model; if per-leg invalidation is introduced in a future story, a
partial/stale total can be revisited then.

> **Scope note -- trip list summary.** Showing the total duration in the trip list (1.1.2)
> would require loading leg data per trip in the list query, which is materially larger
> scope. This is **deferred to a separate story** and is **out of scope** here.

> **Scope note -- stop time.** The future enhancement of "time at stop" (adding stop
> durations to produce a total trip time including rest) is explicitly **out of scope**.
> This story covers driving time only.

## 2. Fields to be Updated

No new domain model or persisted field is required -- the total is **derived**, not stored.

| Field | Location | Type | Purpose |
|-------|----------|------|---------|
| `formattedTotalDuration` (new) | `TripDetailUiState` | `String?` | Pre-computed, display-ready total duration string. `null` when the route is not complete. Follows the established pattern of `formattedTotalDistance`. **Formatting happens in the ViewModel, never in the composable.** |

- The total is computed from the **existing** `Leg.durationSeconds` values already
  accessible via the legs flow; **no new domain field on `Leg` or `Trip`**.
- Summation must use a type that cannot overflow for realistic trips (sum of `Int` seconds
  across up to 24 legs -- accumulate as `Long` to be safe; see Performance).
- The `TripTotalSummary` composable already exists (from 3.2.1) and receives
  `formattedTotalDistance`. It will need a new `formattedTotalDuration` parameter.

---

## 3. Endpoints

**None.** This is a purely local, derived value. No network call, no new Google Routes /
Places request. The data already lives in the local `legs` table populated by story 3.1.1.

## 4. Files to Modify (intent, not solution)

Described by intent; the exact structure is for the propose/design phase.

**UI state**
- `ui/state/TripDetailUiState.kt` -- add the pre-computed total duration field
  (`formattedTotalDuration: String? = null`).

**ViewModel**
- `ui/viewmodel/TripDetailViewModel.kt` -- in the existing `combine` block where
  `formattedTotalDistance` is computed (combining stops and legs flows), also compute the
  total duration: sum the leg `durationSeconds` values **only when the route is complete**,
  format via the existing duration formatter, and emit it in state; otherwise emit `null`.
  The completeness check already exists (it uses the same stops-to-legs ratio).

**Formatting util**
- `ui/util/DurationFormatter.kt` -- reuse `formatDuration(...)` as-is for the total. No
  new formatter is expected; a total trip duration is formatted identically to a single leg
  duration. Only touch this file if a genuinely new formatting need surfaces during design
  (not anticipated).

**Composable(s)**
- `ui/screens/tripdetail/TripTotalSummary.kt` -- extend the existing composable to accept
  and render the total duration alongside the total distance. When the duration is
  available, display it with a label clearly indicating "driving time only". When
  unavailable, display it as such. The composable remains **stateless and purely
  presentational** -- it receives display-ready strings and contains no logic.

**Screen**
- `ui/screens/tripdetail/TripDetailScreen.kt` -- pass the new `formattedTotalDuration`
  from `UiState` to `TripTotalSummary`. Update any existing preview functions that
  instantiate `TripTotalSummary` to include the new parameter.

**Strings**
- `res/values/strings.xml` (UK English base) -- add user-facing strings for the total
  duration label (clearly indicating "driving time only") and the unavailable variant.
  Update `values-it/strings.xml` and `values-es-rES/strings.xml` with translated
  equivalents. Use the ellipsis character where relevant, not three dots.

**Previews**
- Update/extend previews in `TripTotalSummary.kt` and `TripDetailScreen.kt` to cover the
  total duration in: available state, unavailable state, and combinations with total
  distance (both available, distance available but duration unavailable, etc.) -- so every
  new `UiState` field has non-default preview coverage.

## 5. Unit Testing

Follow the project testing guidelines (JUnit 4, MockK, GIVEN/WHEN/THEN names, extract
expected value before asserting, >= 95% coverage, `createViewModel(...)` factory helper).

**ViewModel tests (`TripDetailViewModelTest`)** -- behaviour via observed `uiState`:
- GIVEN a complete set of legs WHEN legs are observed THEN `formattedTotalDuration` equals
  the formatted sum of all leg durations.
- GIVEN two legs of 3600s and 1800s WHEN observed THEN the total reflects 5400s formatted
  as the expected duration string (assert the exact expected formatted string, computed
  independently of the production summation).
- GIVEN no legs but >= 2 placed stops (route not yet calculated / invalidated) WHEN observed
  THEN `formattedTotalDuration` is `null` (unavailable).
- GIVEN fewer legs than expected for the placed stops WHEN observed THEN the total is
  `null` (guards the completeness rule).
- GIVEN fewer than two placed stops WHEN observed THEN the total is `null` (no route
  possible).
- GIVEN legs then a stop mutation that invalidates the route WHEN observed THEN the total
  transitions to `null`.
- Verify the total uses the same formatting function as individual legs
  (`formatDuration`), consistent with existing `DurationFormatter` tests.

**Formatter** -- `DurationFormatterTest` already covers `formatDuration`. Add a case only
if a new edge case relevant to summation surfaces (e.g. very large totals exceeding a

- Total duration and total distance are both visible simultaneously when both are available.
- Use `onNodeWithText` / `onAllNodesWithText[index]` where the value collides with a leg

**Test files required:** update existing `TripDetailViewModelTest` and

## 7. Security -- Issues & Mitigations

- **No new attack surface.** No new endpoint, no new input, no new permission. The total
  is derived from data already stored locally.
- **No secrets involved.** No API keys touched (no new network call).
- **Integer summation integrity.** Ensure summation cannot overflow or produce a negative
  value from corrupted data; clamp/validate defensively and treat implausible values as
  unavailable rather than rendering garbage. Low severity -- `Int` seconds across 24 legs
  cannot realistically overflow even an `Int`, but using `Long` accumulation is a free
  safeguard.

---

## 8. Performance -- Issues & Mitigations

- **Cheap computation.** Summation over <= 24 legs is trivial; runs inside the existing
  legs/stops combine block -- no extra flow, DB query, or network round-trip.
- **Compute off the UI thread / in the ViewModel.** Formatting and summation must happen
  in the ViewModel (already the case for total distance), keeping the composable purely
  presentational and avoiding recomposition-time work.
- **Avoid redundant recomputation.** Recompute only when `legs` (or the stop set feeding
  the completeness check) actually changes; reuse the existing `combine` block rather than
  adding a new subscription.
- **Overflow safety.** Accumulate the sum in a type that cannot overflow for the maximum
  supported stops/durations (`Long` accumulator is safe even for extreme values).

---

## 9. GDPR & Sensitive Information -- Issues & Mitigations

- **No personal data processed or created.** The total is an aggregate number derived from
  route data already stored on-device; it is not personal data on its own.
- **No new data collection, storage, or transmission.** Nothing leaves the device; nothing
  new is persisted.
- **Analytics.** If any analytics event is added, log only non-identifying facts (e.g. that
  a total was displayed) and **never** raw coordinates, place names, or precise durations
  that could reveal a user's location or itinerary. Prefer adding **no** new analytics for
  this passive display unless there is a clear product need.

---

## 10. Other Non-Functional Requirements

- **Accessibility.** The total duration must have a meaningful, screen-reader-friendly
  label (content description) and adequate contrast/typography via Material 3 theme tokens;
  do not rely on colour alone to signal "unavailable". The "driving time only" qualification
  must also be accessible to screen readers.
- **Localisation.** All user-facing text extracted to `strings.xml` (UK English base) and
  propagated to all present locale files (IT, ES). Duration formatting is
  locale-independent (uses integer hours/minutes with no decimal separators).
- **Consistency.** Visual style must match the existing `TripTotalSummary` layout, which
  already displays total distance -- same padding, `onSurfaceVariant` treatment, Material 3
  typography. The duration row should feel like a natural extension of the summary area,
  not a disconnected element.
- **State minimalism (MVI).** Add only the field the UI truly needs
  (`formattedTotalDuration`); keep `UiState` immutable and the composable stateless.
  Extract any new literals to private constants.
- **Configuration changes.** Because the value is derived in the ViewModel from observed
  flows, it survives rotation without extra handling.

   alongside the existing total distance.

## Original user story

### 3.2.2 — See Total Estimated Duration of the Roadtrip

**Epic:** Route Calculation
**Feature:** Trip Totals

### User Story

As a user, I want to see the total estimated duration of the entire roadtrip so that I can understand how long the journey will take.

### Description

The trip overview displays the sum of all leg durations as the total estimated driving time. This is pure driving time — it does not include time spent at stops.

### Acceptance Criteria

- Total duration is displayed on the trip overview screen.
- It equals the sum of all individual leg durations.
- It is clearly labelled as driving time only (does not include stop duration).
- It updates when the route is recalculated.
- If any leg is uncalculated, the total is shown as unavailable or partial with a warning.

### Technical Notes

- Computed from stored `Leg.durationSeconds` values — no additional API call needed.
- Future enhancement: allow users to set a "time at stop" per stop, and show total trip time (driving + stops) alongside pure driving time.
