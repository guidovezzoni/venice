# 9.2.2 — Report Failures to Crashlytics

**Epic:** Analytics
**Feature:** Analytics Destinations

## User Story

As a developer, I want handled failures and crashes reported to Crashlytics, so that I learn about
problems users hit in the wild instead of only the ones I can reproduce.

## Description

The app has no crash reporting at all: no Crashlytics, no
`Thread.setDefaultUncaughtExceptionHandler`, nothing. Crashes are currently invisible.

Separately, the app already knows about a class of problems it never reports — every `operation_failed`
event represents a failure that was caught and shown to the user. Those are exactly the events worth
recording as non-fatals, because they describe things that went wrong without taking the process down.

This story adds a Crashlytics provider as a **deliberately separate provider** from the Firebase
Analytics one. Keeping them independent means the product-analytics backend can be swapped or dropped
later without losing crash reporting, which is the more operationally critical of the two.

The provider no-ops its `logEvent` for events it does not care about, subscribing only to
`OperationFailed` and ignoring everything else, without the analytics provider or any call site knowing
it exists.

### Non-fatals come from the exception channel, not the event

This is the part most likely to be got wrong. `FirebaseCrashlytics.recordException()` requires a real
`Throwable` — that is where the **stack trace** comes from, and the stack trace is essentially the whole
value of a non-fatal report. But `AnalyticsEvent.OperationFailed` deliberately carries only two bounded
enum values (`operation`, `error_type`) so that no free text or PII can reach product analytics. It has
nowhere to put a throwable.

So the non-fatal is driven by **`trackException(throwable, operation)`** — the separate channel added in
9.1.1 — not by the `operation_failed` event. Both fire on a failure path and they answer different
questions:

| Channel | This provider | Carries | Answers |
|---------|---------------|---------|---------|
| `trackException(throwable, operation)` | records a non-fatal | full throwable and stack trace | *where and why* it failed |
| `logEvent(OperationFailed(...))` | adds `error_type` as a custom key for grouping | bounded enums only | *how often* it failed |

Deriving the non-fatal from the event instead would mean synthesising a throwable at the provider,
producing a stack trace pointing at the analytics layer rather than the failure site — technically a
report, practically useless.

Depends on 9.1.1 for the exception channel, and on 9.1.2 for the `error_type` classification that makes
the non-fatals groupable rather than a wall of distinct raw messages.

## Acceptance Criteria

1. **Dependencies added via the version catalog** — `firebase-crashlytics` and the
   `firebase-crashlytics-gradle` plugin. No hardcoded versions.
2. **Crash reporting works** — an uncaught exception in a release-configured build appears in the
   Crashlytics console.
3. **`CrashlyticsAnalyticsProvider` handles only `OperationFailed`** in its `logEvent`, no-oping for
   every other event.
4. **Non-fatals are recorded from `trackException`**, passing the **real throwable** to
   `recordException` so the report carries the stack trace from the failure site.
5. **`operation` and `error_type` are attached as custom keys** so non-fatals can be grouped and
   filtered in the console.
6. **A non-fatal is never synthesised from an `OperationFailed` event** — doing so would produce a stack
   trace pointing at the analytics layer instead of the failure site.
7. **No personal data reaches Crashlytics custom keys** — they carry only bounded enum values from the
   tracking plan. No place names, no coordinates, no identifiers.
8. **Exception messages are accepted in the throwable but never copied into a custom key or an event
   parameter** — the stack trace is the diagnostic payload, and it stays on the crash-reporting channel.
9. **Registered with a single `@Binds @IntoSet`**, independent of the Firebase Analytics binding.
10. **Removing the Firebase Analytics provider leaves Crashlytics working** — verified by temporarily
    commenting out the analytics binding and confirming the build succeeds and crash reporting still
    functions.
11. **No Crashlytics type appears outside `core/analytics` and `di`.**
12. **Native symbol upload is configured** for release builds, or its absence is explicitly recorded as
    accepted.
13. **Debug and release both build.**
14. **On-device verification**: force a handled failure (airplane mode during route calculation) and
    confirm a non-fatal appears in the console **with a stack trace pointing at the failure site**, plus
    the expected custom keys; separately force a crash and confirm it is reported.

## Analytics

No new events. This story adds a second, filtered destination for signals that already exist.

| Channel | Reaches Crashlytics as | Payload |
|---------|------------------------|---------|
| `trackException(throwable, operation)` | non-fatal report | throwable + stack trace, `operation` custom key |
| `operation_failed` event | `error_type` custom key for grouping | bounded enums only |
| all other events | not sent | — |

**User properties**: the provider must implement `setUserProperty` because the interface requires it.
Forwarding them as Crashlytics custom keys is genuinely useful — knowing whether a crashing user is on
metric or imperial narrows a bug faster — so the default is to forward both. If refinement decides
otherwise, the method no-ops with a recorded reason rather than being left ambiguous.

## Technical Notes

- **Independence has a documented limit.** Crashlytics is itself a Firebase product and still requires
  the `google-services` plugin and `google-services.json`. If Firebase Analytics is dropped later, the
  SDK dependency and the `@IntoSet` binding go, but the Gradle plumbing stays. Worth stating plainly so
  the separation is not mistaken for more than it is.
- If 9.2.1 has already landed, the `google-services` plumbing exists and this story only adds the
  Crashlytics artefacts. If this story is ever done *first*, it inherits that setup work.
- Crashlytics collection is enabled by default and starts reporting at process start. Since consent is
  assumed until 9.3.1, that is accepted here — but note that `setCrashlyticsCollectionEnabled` is the
  hook 9.3.1 will need, and it must be settable *before* the SDK initialises to be meaningful.
- Debug builds report crashes too, which pollutes the console with development noise. Decide during
  refinement whether to disable collection in debug; the `applicationIdSuffix = ".debug"` at least keeps
  them separable.
- Non-fatals are throttled by the SDK. A high-frequency failure will not produce one report per
  occurrence, so counts in Crashlytics are not a substitute for the `operation_failed` counts in
  Analytics. The two answer different questions.
- `core/analytics` is not Kover-excluded — the provider needs tests clearing the 95% bound, with
  `FirebaseCrashlytics` mocked.
- Conventions: `docs/guidelines/guidelines-analytics.md`.
