# 8.3.1 — Spike: Sharing Model Design

**Epic:** Cloud Sync & Multi-User
**Feature:** Trip Sharing

## User Story

As a developer, I want to design the trip sharing model so that we have a clear plan for permissions, invitations, and data access before implementing sharing features.

## Description

Before implementing trip sharing, we need to decide on the sharing granularity (per-trip), the permission model (owner/editor/viewer), and the invitation flow (email invite, link, in-app). This story produces a design document covering the data model, RLS policy changes, and UX flow.

## Acceptance Criteria

- A written design covers the sharing data model (e.g. a `trip_members` join table with role column).
- Permission levels are defined (at minimum: owner, editor).
- The invitation flow is described (how a user shares a trip, how the recipient accepts).
- RLS policy changes are specified to allow shared access while preventing unauthorised access.
- Edge cases are addressed: what happens when the owner deletes a shared trip, when a member is removed, when a non-registered email is invited.

## Technical Notes

- **Join table:** A `trip_members(trip_id, user_id, role, invited_at, accepted_at)` table is the standard approach.
- **RLS:** Policies would change from `user_id = auth.uid()` to `EXISTS (SELECT 1 FROM trip_members WHERE trip_id = trips.id AND user_id = auth.uid())`.
- **Invitation:** Supabase does not have built-in invitation management — this would need custom logic (e.g. store pending invites by email, resolve on sign-up).
