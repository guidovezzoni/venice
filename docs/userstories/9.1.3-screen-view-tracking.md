# 9.1.3 — Fire Screen View Events from Navigation

**Epic:** Analytics
**Feature:** Analytics Foundation

## User Story

As a product owner, I want screen view events to reflect what the user actually saw, so that screen
counts and funnel steps are trustworthy rather than systematically wrong.

## Description

`screen_viewed` is currently emitted from each ViewModel's `init` block. A ViewModel is created once
per navigation entry and survives while that entry stays on the back stack, which makes the event fire
at the wrong times in both directions:

- **Under-counts.** Navigating from trip detail back to the trip list does not recreate
  `TripListViewModel`, so no `screen_viewed` fires — even though the user is looking at the screen
  again. Any back-navigation is invisible.
- **Over-counts.** After process death, restoring the screen recreates the ViewModel and fires a second
  `screen_viewed` for a screen the user never navigated to.

Both distortions land on the same events used for funnel analysis, so they are not cosmetic.

The fix is to derive screen views from the single source of truth for what is on screen: the navigation
controller's current destination. `MainScreen` already owns the `NavHost` with two routes.

A new `MainViewModel` receives the screen and emits the event, so the composable only wires a flow to
a callback and holds no logic — consistent with the project rule that composables are purely
presentational. Route-to-screen mapping lives in a testable function on `AnalyticsScreen`, not in the
composable.

Depends on 9.1.2 (the `AnalyticsScreen` enum).

## Acceptance Criteria

1. **No screen tracking in ViewModel `init`** — the calls are removed from both `TripListViewModel` and
   `TripDetailViewModel`.
2. **Screen views are driven by navigation destination changes.**
3. **Back-navigation fires the event** — returning from trip detail to the trip list emits
   `screen_viewed { screen_name: trip_list }`.
4. **Consecutive duplicates are suppressed** — a destination change that resolves to the same screen
   does not emit twice.
5. **Process-death restore does not emit a spurious event** for a screen the user did not navigate to.
6. **Route-to-screen mapping is a pure, unit-tested function**, covering both known routes and an
   unrecognised route.
7. **An unrecognised route emits nothing** rather than an `unknown` screen event — a route with no
   mapping is a bug to notice, not data to record.
8. **The composable contains no logic** beyond connecting the navigation flow to the ViewModel callback.
9. **On-device verification**: navigate list → detail → back → detail and confirm via
   `adb logcat -s Analytics` that four `screen_viewed` events fire with the correct screen names in
   order.

## Analytics

| Event | Parameters | Change |
|-------|-----------|--------|
| `screen_viewed` | `screen_name` | Name and parameters unchanged; **trigger moves** from ViewModel `init` to navigation destination changes |

No new events. Event volume will rise once back-navigation is counted — expected, and the reason the
current numbers should not be compared across this change.

## Technical Notes

- `navController.currentBackStackEntryFlow` is the intended source. Collect it from a `LaunchedEffect`
  keyed on the controller, map to `AnalyticsScreen`, apply `distinctUntilChanged()`, and forward to the
  ViewModel.
- `distinctUntilChanged()` on the mapped screen — not on the back stack entry — is what satisfies
  AC 4, since a new entry for the same route should not re-emit.
- The trip detail route is parameterised (`ROUTE_TRIP_DETAIL` carries a trip id). Map on the route
  *pattern*, not the resolved path, or every trip will look like a distinct screen. Never put the trip
  id in the event.
- AC 5 is the subtle one and the easiest to regress. Worth an explicit check that the restore path
  goes through a destination *change* rather than a ViewModel recreation.
- `MainViewModel` is `@HiltViewModel` and therefore excluded from Kover's annotation filter, but its
  logic should still be tested via the public callback. `AnalyticsScreen.fromRoute` is not excluded and
  needs full boundary coverage.
- Conventions: `docs/guidelines/guidelines-analytics.md`.
